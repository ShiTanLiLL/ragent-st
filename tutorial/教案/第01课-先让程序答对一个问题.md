# 第 1 课：先让程序答对一个问题

> 状态：已完成。学生已完成环境验证，亲自观察编译红灯，并运行已知问题与未知问题测试完成最终验收。

## 1. 前言

我们最终要理解的是一个能上传企业文档、检索证据、调用大模型并流式回答的 Agentic RAG 系统。但今天它还不存在，所以先不谈向量库、Spring、Agent 或设计模式。

现在只有一个很小却真实的客服需求：

> 用户问退货期限时，程序要回答“签收后 7 天内可申请无理由退货”；用户问到尚未收录的内容时，程序必须诚实说没有找到，不能编造。

这个起点刻意简单。它先让我们看清最短的数据流：

```text
一个问题字符串
  ↓
判断是否命中当前唯一知识
  ↓
一个回答字符串
```

当前只有一条知识和一种处理方式，没有理由创建知识库接口、模型 Provider、Repository、工厂或配置中心。后续政策变多时，我们会让这份简单代码自然暴露问题，再重构。

## 2. 主要内容

本课按四个交互小节推进：

1. 共同确认已知问题的输入与预期回答。
2. 先写测试，亲眼看到它因为产品代码不存在而失败。
3. 写刚好让已知问题通过的最小实现，并由学生运行测试。
4. 再加入未知问题测试和诚实兜底，完成本课验收。

每完成一个小节都暂停。学生运行测试、反馈结果和提问后，才进入下一小节。

## 3. 技术要点

### 3.0 课前环境基线

本课假设学生使用刚安装的 VS Code，没有插件、JDK 或 Maven。进入第一个失败测试前，先完成一次独立的环境验证：

```text
Windows 侧：VS Code + WSL 扩展
       ↓ 连接
WSL 侧：项目文件 + JDK 17 + Maven + Java 扩展
```

- 编码工作区只打开 `ragent-st`，避免把原项目误当成当前练习代码。
- 本项目由 `pom.xml` 声明 Java 17 和 JUnit 5；JDK 负责 Java 编译与运行，Maven 负责下载依赖并执行构建和测试。
- Java 扩展包负责代码提示、Maven 项目识别和测试按钮，但不能代替 JDK 与 Maven。
- 当前没有 Java 源文件、测试或 `main` 方法，因此暂时看不到可用的 Java 运行按钮是正常现象；不创建 `launch.json` 来制造一个虚假的入口。
- 环境验证通过且学生反馈结果后，才进入 3.4 的第一个 TDD 循环。

### 3.1 当前坐标

```text
最终系统：文档 → 分块 → 检索 → Prompt → 模型 → 流式回答
                    ↑
本课只实现：问题 → 最小知识判断 → 回答
```

本课还不是完整 RAG。我们只建立未来检索环节最小的业务胚芽，并练习如何让需求通过测试变得可观察。

### 3.2 本课唯一业务对象

计划在正式课堂中创建：

```text
KnowledgeAssistant
  answer(question: String): String
```

- `question`：用户提出的问题，例如 `"退货期限是多久？"`。
- 返回值：当前系统给用户的完整回答。
- 这一课不保存状态；一次调用结束后没有跨请求数据。
- 政策暂时直接写在方法里，因为当前真的只有一条。

不要提前创建 `KnowledgeRepository`、`Retriever`、`AnswerGenerator`、`ModelClient` 等名字。它们此时没有第二种实现，也没有解决已出现的问题。

### 3.3 两个具体业务实例

已知问题：

```text
输入：退货期限是多久？
输出：签收后 7 天内可申请无理由退货。
```

未知问题：

```text
输入：如何开具发票？
输出：暂时没有找到相关知识。
```

这两个例子分别保护 Happy Path 和一条重要业务边界：没有知识时不编造。

### 3.4 第一次 TDD 循环

正式课堂的顺序是：

```text
已知退货问题需求
→ 创建 KnowledgeAssistantTest
→ 运行并看到失败
→ 创建 KnowledgeAssistant 与 answer
→ 只实现退货回答
→ 再次运行并通过
```

第一个失败很可能是“找不到 `KnowledgeAssistant` 类”的编译错误。这同样是有效的红灯：测试准确指出产品能力还不存在。课堂中会结合真实报错解释编译期失败与断言失败的区别。

### 3.5 第二次 TDD 循环

已知问题通过后，再提出“未知问题不能编造”：

```text
未知发票问题需求
→ 增加第二个测试
→ 观察旧实现返回错误结果
→ 增加最小兜底
→ 两个测试都通过
```

此时即使实现里出现一个简单 `if/else` 也可以接受。第 2 课新增多条政策后，它会成为可观察的维护问题；那时再重构。

### 3.6 测试结构

测试会采用 Arrange / Act / Assert：

```text
Arrange：准备助手和问题
Act：调用 answer(question)
Assert：比较实际回答与业务要求
```

这里的重点不是背术语，而是把“准备数据、执行行为、观察结果”分开，让失败位置更容易看懂。

### 3.7 预计文件变化

只有在相应交互节点到达后才创建：

```text
ragent-st/
├── src/test/java/com/shitan/ai/KnowledgeAssistantTest.java
└── src/main/java/com/shitan/ai/KnowledgeAssistant.java
```

本课不创建启动类、HTTP Controller、配置文件、数据库表或后续课程目录。

## 4. 测试与验收

### 4.1 已知问题测试

目的：证明系统已经拥有第一条真实知识回答能力。

输入：`退货期限是多久？`

预期：精确返回 `签收后 7 天内可申请无理由退货。`

它证明：一个用户问题已经能穿过最小业务逻辑变成确定回答。

### 4.2 未知问题测试

目的：证明系统不会对未收录知识伪造答案。

输入：`如何开具发票？`

预期：返回 `暂时没有找到相关知识。`

它证明：最小系统已有明确知识边界。

### 4.3 学生实际验收

代码到达每个节点后，由学生在 VS Code Testing 面板或项目终端亲自运行。届时聊天中会给出准确命令、预期红/绿结果和反馈格式，不把临时操作步骤提前塞进教案。

本课结束前需要学生能够回答：

- 当前输入和输出各是什么？
- 哪个分支表示“命中知识”，哪个表示“没有知识”？
- 为什么现在不需要数据库、模型和接口？
- 测试失败如何证明需求尚未实现？

## 5. 总结

本课结束后，系统将第一次具备“根据一条已知知识回答问题，并在未知时诚实兜底”的能力。它很小，但可运行、可测试，而且没有任何未来设计。

它也会留下一个真实问题：第二条、第三条政策到来后，继续添加判断分支会越来越难维护。这个问题将在第 2 课真正出现后，再推动知识数据与匹配逻辑演化。

验收完成时，老师会暂停开发，提示学生查看 `git status` 和 `git diff`，给出建议的暂存范围与中文 commit message；commit 必须由学生亲自执行。
