# 第 15 课：只靠一种检索，精确编号和自然语言难以兼得

## 先看两条通路

本课没有改变上传通路，上传仍然是：

```text
上传 HTTP
  → 摄取任务
  → 解析、分块、Embedding
  → knowledge_chunk 表保存正文和向量
```

本课改变的是回答通路：

```text
问题 HTTP
  → ConversationQuestionService 保存用户消息
  → IntentRoutingService 改写、拆问并确定知识库作用域
  → HybridRetrievalService 并行执行
       ├─ VectorSearchChannel：问题 → Embedding → pgvector 语义候选
       └─ KeywordSearchChannel：问题 → 编号/短语 → 文本精确候选
  → 按 Chunk id 去重并用 RRF 融合名次
  → BailianEvidenceReranker 精排候选
  → BailianClient 把前 2 条证据和问题交给 Chat 模型
  → QuestionResponse 返回答案、来源和 evidence
```

一句话概括：上传时文档已经被分块、向量化并存进 PostgreSQL；回答时同一个问题同时走“语义找相似”和“文字找精确”，再把合并后的少量证据交给大模型。

## 为什么上一课的单路向量检索不够

第 14 课以后，问题已经可以被正确地改写、拆分并限制到某个知识库，但具体检索仍然只有向量通道。向量很适合“设备无法启动”和“按电源键没有反应”这种意思相近但字面不同的说法，却可能把 `WX-2048` 这样的错误码看成普通字符。反过来，纯关键词检索能保护编号，却不理解同义表达。

本课只解决这个真实问题：两种召回都保留，不能直接把两种分数相加，因为余弦相似度和关键词出现次数不是同一把尺子。先分别取名次，再用 Reciprocal Rank Fusion（RRF，倒数排名融合）统一比较；之后只把很小的候选集交给精排模型，最后最多把两条证据放进回答 Prompt。

## 完整执行链和对象职责

1. `IntentRoutingService` 把第 14 课的 `knowledgeBaseIds` 原样交给 `BailianRagAssistant`，所以混合检索不会越过已选定的知识库。
2. `HybridRetrievalService` 为每个 `SearchChannel` 创建一个 `CompletableFuture`。它使用 Spring 的 `retrievalExecutor` 线程池并行等待两路结果；某一路报错只变成空结果，不影响另一条路。
3. `VectorSearchChannel` 先调用 `BailianClient.createEmbedding`，然后让 `KnowledgeRepository.searchVectorCandidates` 用 pgvector 按余弦距离取前 8 条。
4. `KeywordSearchChannel` 从问题中取出字母数字编号、数字和 2～8 个汉字短语，再让仓库读取同一作用域的成功片段并计算精确命中分。
5. `HybridRetrievalService.fuseByRrf` 以 Chunk 的 `id` 去重。一个 Chunk 如果被两条通道都找到，就保留 `channels=["keyword","vector"]` 以及两种原始分数；它在两个通道都靠前时，RRF 分更高。
6. 候选先截到 6 条，再交给 `BailianEvidenceReranker`。当前为了复用已经配置好的百炼 Chat 网关，模型被要求返回 `{"results":[{"index":0,"score":0.98}]}`；这一步是“精排契约”的教学实现，不是把官方专用 Rerank 地址硬编码进主链。
7. `BailianRagAssistant` 只把精排后的前 2 条转成 `KnowledgeEntry`，交给 `BailianClient.generateAnswer`。`KnowledgeAnswer` 同时保留结构化 `evidence`，所以测试和 HTTP 调用者能看到模型实际使用了哪些证据。

```text
问题 q
  ├─ vector：Embedding(q) → [chunk A, chunk B, ...]
  └─ keyword：提取 WX-2048 → [chunk A, ...]
                 ↓
          id 去重 + RRF 名次融合
                 ↓  候选最多 6 条
             Chat 精排
                 ↓  上下文最多 2 条
          Chat 生成受证据约束的回答
```

## 测试里的真实数据如何流动

`HybridRetrievalApiLiveIT` 先上传：

```markdown
# 设备售后
## 故障代码 WX-2048
遇到 WX-2048 时请先断电 30 秒，再重新启动。
## 无法开机
设备按下电源键没有反应时，请检查电源线。
```

第一问是 `设备报错 WX-2048 怎么处理？`。关键词通道命中 `WX-2048`，向量通道也找到同一 Chunk；返回的中间 evidence 类似：

```json
{
  "title": "设备售后 / 故障代码 WX-2048",
  "channels": ["keyword", "vector"],
  "vectorScore": 0.88,
  "keywordScore": 28.0,
  "rrfScore": 0.0328,
  "rerankScore": 0.98
}
```

第二问是 `设备按电源键没有反应怎么办？`。它没有固定错误码，向量通道把它带到 `无法开机`，关键词通道可能没有命中；这不是失败，而是“这一问主要由语义通道负责”。测试故意打印两次响应，帮助观察通道列表、原始分数、RRF 分数、精排分数和最终答案。

## 为什么需要这些新类

- `SearchChannel`：两种检索已经有不同输入处理和数据库动作，继续塞进一个方法会让“并行、异常隔离、融合”与具体算法搅在一起。接口只约定“给我问题，返回候选”。
- `SearchQuery` / `SearchChannelResult`：把作用域、问题和候选耗时作为一次通道执行的输入输出，避免在异步闭包里依赖零散变量。
- `RetrievedEvidence`：`KnowledgeEntry` 只适合交给答案模型；本课还要携带 channel、向量分、关键词分、RRF 分和精排分，所以新增一个“检索过程中的证据”对象。
- `HybridRetrievalService`：它是本课主角，负责调度和后处理，不负责写 SQL，也不负责拼 Chat JSON。
- `EvidenceReranker`：精排模型以后可能更换；现在只有百炼实现，所以先抽出真正被两处需要的契约，不预埋更多 Provider。

## 几个容易混淆的技术点

### 为什么不把两个分数直接相加？

向量分大约在 0～1 之间，关键词分可能是 28、40；直接相加会让关键词权重天然更大。RRF 不关心原始分数，只看每条通道的第几名：第 `rank` 名贡献 `1 / (60 + rank)`。同一条证据同时出现在两条通道里，就得到两份贡献。

### `CompletableFuture` 和线程池解决什么？

一个 HTTP 请求线程不必先等向量查询结束，再等关键词查询结束。两个 `supplyAsync` 把等待工作放进受限的 `retrievalExecutor`；请求线程最后 `join` 两个结果。每个请求的候选列表独立，线程池和 Spring 单例服务是共享的，但本课没有把候选保存到共享可变字段中。

### 为什么通道异常要变成空列表？

向量模型短暂超时不应让关键词编号检索也完全失效，反过来也一样。`searchSafely` 是本课明确的降级边界；若两路都空，系统才返回“没有找到足够相关的知识”。

### 精排为什么也允许降级？

精排是候选的第二次排序，不是知识本身。百炼返回格式不对或网络失败时，`BailianEvidenceReranker` 保留 RRF 候选继续回答；如果模型确实返回了分数但最高分低于 `0.25`，才触发证据门槛并拒绝把无关内容送给答案模型。

### 这里的 Rerank 是官方独立模型吗？

百炼确实提供专用 Rerank 能力，但它需要单独的工作空间服务地址和模型配置。本课先复用已经验证过的 Chat 网关，只练习“候选输入 → 排序 JSON → 重新排序”的数据契约。后续若换成专用 Rerank，只替换 `EvidenceReranker` 实现，`HybridRetrievalService` 的输入输出不变。

## 本课边界

本课没有实现 Elasticsearch/BM25、缓存、分布式任务、真正的多租户权限或完整引用展示；关键词通道为了可读性读取作用域内成功片段后在 Java 中计分。真实数据量增大后，这会成为下一步性能需求，而不是现在提前设计的理由。
