# 第17课：并发上涨时，先保护单机资源

## 先看两条业务通路

这一课位于“可靠性”层：上一课已经能在模型失败时切换候选，但如果请求同时涌入，模型调用和文档摄取仍可能把线程、连接和外部模型额度一起压满。

```text
回答问题：HTTP → 会话/意图/检索 → ModelRoutingService
          → modelAdmissionGate → 百炼 Chat → 返回答案 → 释放名额

存知识：HTTP 上传 → IngestionTaskService
        → ingestionAdmissionGate → 任务/线程池 → Pipeline
        → 解析、向量化、发布 → 任务完成 → 释放名额
```

两条通路都先申请一个“名额”。申请不到时，本课选择快速失败并提示稍后重试，而不是让请求无限排队。名额只是内存中的单机状态，数据库仍保存文档、任务和阶段结果；这一课还没有跨进程协调。

## 1. 为什么上一课的模型路由还不够

第16课解决的是“某个模型坏了怎么办”：候选模型按档位和优先级切换，并用 CLOSED、OPEN、HALF_OPEN 隔离故障。但它默认每个候选都可以立刻被调用。

现在出现的是另一种问题：模型没有坏，只是同时有很多请求。若每个请求都进入外部 HTTP 调用，等待响应的线程会越来越多；摄取任务也可能不断堆进线程池。于是我们先增加一个最小的单机容量控制，不提前设计 Redis、消息队列或分布式限流。

## 2. 本课新增职责

| 对象 | 本课新增或保留的职责 | 不负责什么 |
| --- | --- | --- |
| `AdmissionGate` | 用有限名额和有界等待保护一种资源；成功后发出 `Lease` | 不知道模型、文档或数据库业务 |
| `AdmissionGate.Lease` | 表示“这个请求占着一个名额”；关闭时归还，重复关闭也只归还一次 | 不负责决定请求是否成功 |
| `ModelRoutingService` | 在真正调用模型前申请模型名额，在 `finally` 中释放 | 不把容量不足误判为模型故障 |
| `IngestionTaskService` | 在创建 pending 文档和任务前申请摄取名额，后台执行结束后释放 | 不让无名额的请求留下无人处理的 pending 任务 |
| `RagentApplication` | 用配置创建两个不同闸门 Bean | 不把配置变成跨实例共享状态 |

这里的两个闸门不是同一个东西。模型调用和文档摄取消耗的是不同资源，所以分别配置；例如默认模型同时最多4个，摄取同时最多2个。

## 4. `AdmissionGate` 的关键 Java 语法

`Semaphore` 可以先理解成一个装着“许可牌”的盒子。构造 `new Semaphore(1, true)` 就是放入一张牌，并要求等待者尽量按进入顺序拿牌。`tryAcquire(等待时间)` 在规定时间内拿不到牌就返回 `false`。

代码没有把 `Semaphore` 直接交给业务，而是把成功拿到的牌包装成 `Lease`。`Lease implements AutoCloseable` 表示它可以放进 `try/finally` 的资源释放结构中；本课主要使用显式 `finally`，因为模型调用和后台任务都可能抛异常。

`Lease` 中的 `AtomicBoolean released` 是“只允许第一次关闭生效”的开关。它保护的是同一个任务的多个结束路径：正常返回、异常捕获、取消或重复提交保护都可能走到清理代码。多个请求不会共享同一个租约；它们共享的是闸门里的许可数量。

## 5. 模型回答链：容量不足不是模型故障

按 [`ModelRoutingService.generate(...)`](/home/shitanli/ln_rebuild/ragent/ragent-st/src/main/java/com/shitan/ai/ModelRoutingService.java:65) 阅读：

1. `orderedCandidates(tier)` 先按请求档位和优先级排列模型候选。
2. `candidate.tryAcquire()` 处理第16课的模型健康状态；OPEN 候选会跳过。
3. `admissionGate.tryAcquire()` 再处理单机总模型并发。如果返回空，直接抛出“模型并发名额已用尽”，不把这个情况标记成候选模型失败。
4. 真正调用 `invoker.invoke(...)`，成功就把候选标为 CLOSED 并返回答案；外部调用失败才标记该候选失败并尝试下一个候选。
5. 无论成功、异常还是中断，`finally` 都关闭租约。

如果候选正好处于 `HALF_OPEN`，但机器容量没有放行，本次根本没有调用模型。`releaseProbeWithoutCall()` 会把这次“没有发生的探测”资格还回去，避免一个健康候选因为本机拥挤而永远卡在半开状态。

因此这里有两个不同状态：模型健康状态回答“这个模型最近是否可用”，闸门容量回答“此刻这台机器还能不能再接一个调用”。把容量不足算成模型故障，会错误地把健康模型放进 OPEN，这是本课特意避免的边界。

## 6. 摄取链：为什么在创建 pending 之前申请

按 [`IngestionTaskService.submit(...)`](/home/shitanli/ln_rebuild/ragent/ragent-st/src/main/java/com/shitan/ai/IngestionTaskService.java:55) 阅读：

1. `acquireIngestionLease()` 最多等待配置的毫秒数。
2. 拿到租约后才保存原文、创建 `pending` 文档和插入任务记录。
3. `ingestionExecutor.execute(...)` 只提交后台工作，HTTP 请求仍然很快返回任务编号。
4. 后台 `execute(...)` 取得 pending 任务，调用既有 Pipeline，最后在 `finally` 释放租约。

这样做的原因很具体：如果先写数据库、后申请名额，名额不足时会留下一个没有线程负责的 pending 任务。远程 URL 上传和 `retry(...)` 也采用同样顺序。旧的四参数构造器仍使用 `AdmissionGate.unbounded()`，只是为了让前面课程的手写测试继续表达原来的行为；Spring 实际启动时注入的是有界 Bean。

## 8. 本课边界与下一步

`AdmissionGate` 只存在当前 JVM：应用重启后名额归零，多台应用实例之间也互不知道。它适合先解决“单机线程和外部调用不要无限堆积”的真实问题。只有部署多实例、单机保护失效或需要跨实例公平排队时，才有理由引入 Redis、消息队列或网关限流。本课不提前实现那些组件。

### 为什么申请名额既可能返回空，也可能抛异常

`tryAcquire()` 有三个结果：拿到名额时返回 `Lease`；正常等完整个期限仍没有名额时返回 `null`；等待期间线程被应用关闭、任务取消等动作中断时抛出 `InterruptedException`。`null` 表示普通业务拥堵，中断异常表示上层要求线程停止等待，二者的恢复和日志含义不同，不能都写成“系统繁忙”。

### Spring 怎样区分两个同类型 Gate

`modelAdmissionGate` 和 `ingestionAdmissionGate` 都是 Spring 单例 Bean。所有请求共享各自 Bean 内的许可数量，每次成功申请得到的 `Lease` 则只属于当前调用。因为两个 Bean 的 Java 类型相同，构造参数必须使用 `@Qualifier` 指定名称；若只按类型注入，Spring 会因无法选择而拒绝启动。

### 两条通路控制的粒度并不相同

摄取 Gate 的一个名额覆盖一项完整文档任务，从 HTTP 受理前一直持有到后台 Pipeline 结束。模型 Gate 的一个名额只覆盖一次具体 Chat 模型调用：一个父问题如果产生多个子问题，会多次申请；首选模型失败后尝试备用模型，也会重新申请。它目前没有覆盖问题改写、摘要和教学版 Rerank 等直接调用 `BailianClient` 的路径，因此应准确称为“答案模型调用容量保护”，而不是“整个问答请求限流”。
