# 第20课：把外部工具接进来，同时守住安全边界

## 先看四条通路

这一课位于“Agent 工具接入与安全执行层”。第19课的 Agent 循环不再只认识同一进程里的 Java 工具，而是能通过 MCP 发现和调用另一个 HTTP 服务；有副作用的工具必须先读手册，再停下来等人确认。

```text
启动发现：Spring 创建 McpToolClient
         → 请求远端 MCP tools/list
         → McpRemoteAgentTool 把远端 Schema 适配成 AgentTool
         → AgentService 将本地工具和远端工具合并成白名单

只读通路：POST /api/agent/tasks
         → AgentService 把可见工具交给决策模型
         → 模型选择远端 order_status
         → McpToolClient 发送 tools/call
         → 订单事实成为 AgentStep.observation，再进入下一轮

写操作通路：模型先选择 load_skill
           → SkillManualAgentTool 返回退货办理手册
           → 下一轮才看见 return_request_create
           → AgentService 不调用远端，而把工具名和参数冻结到 agent_confirmation
           → 会话变成 waiting_confirmation

确认通路：POST /api/agent/confirmations/{id}
         → AgentService 按 userId 读取被冻结的工具和参数
         → 原子抢占 pending 确认
         → McpToolClient 才真正调用远端写工具
         → 保存 Observation，恢复 Agent 循环并生成最终回答
```

用一句话概括：MCP 负责“远端有哪些工具、怎样按统一格式调用”，主应用负责“哪些工具可以展示、什么时候能执行、由谁确认、执行哪一份参数”。协议互通不等于业务安全。

## 1. 第19课还缺什么

第19课的 `order_lookup` 是主应用内的一个 Spring Bean。这样的本地工具很容易理解，但每接一个独立业务系统，都要在主应用里手写客户端、工具描述和调用桥梁，工具服务也不能主动公开自己的能力。

更现实的问题是，工具不再都只读。“查询订单状态”失败最多是少一条信息；“创建退货申请”会修改另一个系统。不能因为模型输出了一个工具名，Java 就立即执行。

因此本课只解决三个已经出现的需求：

1. 远端订单服务用统一协议公布工具，不要求 Agent 在编译期认识服务端 Java 类；
2. 复杂写操作先按需加载业务手册，避免所有长规则一直占用模型上下文；
3. 写操作参数先由服务端冻结，人只批准或拒绝，批准请求不能趁机换参数。

## 2. 核心对象怎样分工

```text
McpOrderServer
  对外公布 tools/list，并执行 tools/call
         │ HTTP + JSON-RPC
         ▼
McpToolClient
  解析工具 Schema，发送远端调用
         │ McpDiscoveredTool
         ▼
McpRemoteAgentTool
  把远端工具翻译成 AgentTool
         │
         ▼
AgentService
  控制可见性、Skill、确认、幂等和 Agent 循环
         │
         ├─ SkillManualAgentTool：读取本地版本化手册
         └─ AgentRepository：保存 session、step、confirmation
```

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `McpOrderServer` | 公开远端工具 Schema，校验 MCP 请求，执行教学订单查询/退货创建 | 不知道主应用的 Agent 循环，也不代替用户确认 |
| `McpToolClient` | 组装 MCP HTTP/JSON-RPC，请求 `tools/list`、`tools/call`，解析响应 | 不决定工具是否安全，不控制会话状态 |
| `McpRemoteAgentTool` | 把远端工具适配成现有 `AgentTool` | 不复制远端业务逻辑 |
| `SkillManualAgentTool` | 按 `skillCode` 返回复杂操作说明 | 不创建退货申请 |
| `AgentService` | 合并白名单、隐藏未解锁工具、冻结参数、等待确认、恢复循环 | 不实现订单系统 |
| `AgentRepository` | 持久化确认并用条件更新防止重复批准 | 不判断工具风险 |
| `SystemHealthService` | 真实检查数据库和 MCP 是否可达 | 不修复故障 |

## 3. MCP 是什么，哪些格式由协议规定

MCP 是 Model Context Protocol。这里先把它理解成“主应用和外部工具服务之间的一套共同语言”。本课使用 Streamable HTTP 传输和 JSON-RPC 2.0 消息。

发现工具时，客户端发送：

```http
POST /mcp
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/list

{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{...}}}
```

服务端返回的核心数据是：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [{
      "name": "order_status",
      "description": "查询订单当前状态",
      "inputSchema": {
        "type": "object",
        "required": ["orderId"]
      },
      "annotations": {"readOnlyHint": true}
    }]
  }
}
```

`tools/list`、`tools/call`、`inputSchema`、`annotations.readOnlyHint` 和 JSON-RPC 外壳来自协议；`order_status`、`orderId` 及其业务含义由我们的订单服务定义。`requiredSkillCode` 不是 MCP 字段，而是主应用根据工具名附加的本地安全策略。

调用工具时，`McpToolClient.callTool()` 发送：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "order_status",
    "arguments": {"orderId": "ORD-1001"},
    "_meta": {"userId": "alice"}
  }
}
```

远端把结果放进 `result.content`。客户端逐个查看内容块，只拼接 `type=text` 的文字；如果 `isError=true`，就转成异常。这里用 Jackson 的 `path()` 是因为协议响应是动态 JSON，暂时没有必要为每层外壳建立许多只使用一次的数据类。

## 4. Adapter 这次为什么自然出现

第19课的 `AgentService` 只认识 `AgentTool`，远端发现结果却是 `McpDiscoveredTool`。如果让 `AgentService` 自己拼 HTTP，它就会同时承担循环控制和 MCP 协议解析。

`McpRemoteAgentTool` 做了一次很窄的翻译：

```text
远端 name/description/inputSchema/readOnlyHint
→ 本地 name()/definition()/readOnly()

本地 execute(arguments, scope)
→ McpToolClient.callTool(name, arguments, scope.userId)
```

这就是 Adapter（适配器）：不改变两边的核心职责，只把一个已有形状转换成另一个已有接口。它不是为了“以后可能扩展”提前创造的；是因为本地 Agent 接口和远端协议数据现在已经真实不同，转换工作已经出现。

## 5. Skill 为什么不是普通工具说明

工具 Schema 只适合短说明：叫什么、做什么、要哪些参数。退货办理却包含前置检查、允许状态、原因来源、确认要求和成功后怎样汇报。如果把所有复杂手册始终放进决策模型输入，每一轮都要重复消耗上下文，而且模型还会过早看到尚不能执行的写工具。

本课采用渐进式加载：

```text
初始工具目录：order_status、load_skill（没有 return_request_create）
→ 模型调用 load_skill(return_request)
→ 手册正文保存成一个 AgentStep Observation
→ AgentService 从已保存历史确认 Skill 真正加载成功
→ 下一轮目录才出现 return_request_create
```

`Skill` 在这里就是一份版本化、按需加载的操作手册。它不是 Java 类自动获得的新权限，也不直接执行写操作。模型嘴上声称“我读过了”没有用；只有数据库里存在成功的 `load_skill` 步骤，`isSkillLoaded()` 才返回 true。

### 四个相似 Tool 类，按“数据还是行为”区分

这四个名字不要并排死记。先问它“只是数据，还是可以执行”，再问它“给谁看”：

| 类型 | 数据还是行为 | 由谁产生 | 交给谁 | 一句话记忆 |
| --- | --- | --- | --- | --- |
| `AgentTool` | 可执行接口 | 主应用定义 | `AgentService` | 所有本地/远端工具进入循环时必须遵守的总插座 |
| `McpDiscoveredTool` | 数据快照 | `McpToolClient` 解析远端 `tools/list` | `McpRemoteAgentTool` | 远端刚寄来的工具说明书 |
| `McpRemoteAgentTool` | 可执行对象 | 客户端用发现快照创建 | `AgentService` | 插在总插座上的远端工具转接头 |
| `AgentToolDefinition` | 数据快照 | 每个 `AgentTool.definition()` 产生 | 决策模型 | 从可执行工具上摘出的、只给模型阅读的菜单项 |

一次转换可以写成：

```text
远端 tools/list JSON
→ McpDiscoveredTool（协议数据已经读进 Java）
→ McpRemoteAgentTool（现在具备 execute 行为，符合 AgentTool）
→ AgentToolDefinition（每轮只把允许模型看到的说明交给模型）
```

`McpDiscoveredTool` 与 `AgentToolDefinition` 字段现在很相似，但来源和生命周期不同。前者证明“远端公布了什么”，后者表示“主应用这一轮允许模型看到什么”。本课保留这层转换，正是因为主应用还会在中间加入 Skill 和确认策略。

### 远端 MCP 工具是什么时候进入 AgentService 的

MCP Server 的源码虽然为了教学方便放在同一个 Maven 工程中，运行时却是独立 Java 进程，不属于 Spring 容器，也不与主应用共享对象：

```text
Java 进程1：McpOrderServerApplication
  监听 127.0.0.1:8091/mcp

Java 进程2：RagentApplication（Spring Boot）
  McpToolClient 通过 HTTP 访问进程1
```

Spring 创建 `AgentService` 时，构造方法先收到所有本地 `AgentTool` Bean，再主动执行一次 `mcpToolClient.discoverAgentTools()`。发现到的远端工具被包装为 `McpRemoteAgentTool`，与本地工具一起放进不可变的 `tools` Map。`runLoop()` 开始前工具执行对象已经装配完毕，不会每轮重新发现。

因此当前启动顺序应是“先 MCP，后 Spring”。如果 Spring 启动时 MCP 不可达，客户端会保留本地工具并继续启动，但这一实例的 `tools` Map 中没有远端工具；后来单独启动 MCP 不会自动刷新目录，需要重启 Spring。这是当前教学版“启动时发现一次”的明确边界。

健康接口会重新请求 `tools/list`，但它只报告连通性，不会偷偷修改 `AgentService` 的工具 Map。

### availableToolDefinitions 为什么必须查看 history

`AgentService.tools` 是“主应用实际上装配了哪些工具”，而 `availableToolDefinitions(history)` 是“这一轮允许模型看见哪些工具”。两者不是同一张清单。

远端写工具从启动时起已经存在于 `tools` Map，方便批准后执行；但在成功加载手册前，它不能出现在模型菜单中。是否已经加载不是一个只活在内存里的布尔值，而是历史中一条已经落库的成功步骤：

```text
toolName = load_skill
toolInput = {"skillCode":"return_request"}
observation 以“已加载 Skill”开头
```

所以该方法必须读取 `history`。这样服务重启、恢复会话之后仍能从数据库恢复解锁状态，也不能靠模型说一句“我已经读过”来伪造解锁。

### 工具发现、Skill 加载需要人手动调用吗

两个“调用”的主体不同：

- 工具发现不需要用户手动触发。Spring 创建 `AgentService` 时，构造方法自动调用 `discoverAgentTools()`。
- Skill 加载不是 Spring 自动做的，也不是用户点击专门接口；它作为普通本地工具 `load_skill` 参加 Agent 循环，由决策模型在某一轮选择。
- 真实生产入口是 `BailianAgentDecisionModel.decide()`：模型会同时看到目标、当前可见工具和历史 Observation，然后输出 `toolName=load_skill`。
- 本课测试为了稳定理解流程，由短脚本代替模型做同一个选择，并没有替换 Skill、MCP 或数据库。

初始菜单里能看到 `load_skill` 的说明，其中明确列出 `return_request`。当目标要求创建退货申请时，模型应当先选择它。手册加载并保存后，下一轮模型才看到 `return_request_create`。

`load_skill` 不由 MCP Server 提供。它是 Agent 主机自己的上下文与安全策略，由本地 `SkillManualAgentTool` 实现；MCP Server 只提供订单领域的 `order_status` 和 `return_request_create`。理论上其他系统也可以通过 MCP 暴露资源或提示，但那是另一种设计，不改变“是否解锁写工具由主应用决定”的边界。

## 6. 为什么 readOnlyHint 仍然不能当权限系统

`readOnlyHint=true` 表示工具声称自己不会修改环境，它帮助主应用选择交互方式。但它是远端提供的元数据，不能独自证明远端实现绝对安全。

本课的最小做法是：远端声明提供风险线索，主应用再根据已知工具建立本地策略。`return_request_create` 被明确视为写工具，并绑定 `return_request` Skill；写工具一律进入确认路径。真实生产环境还会把允许的 MCP Server、工具名和风险级别配置成可信白名单，并在远端再次做身份与权限校验。

## 7. 写操作为什么要“冻结参数”，而不是确认时再传一次

等待确认时保存到 `agent_confirmation` 的不只是一个“是否同意”，还有：

```text
tool_name = return_request_create
tool_input = {"orderId":"ORD-1001","reason":"耳机不合适"}
decision_summary = 订单已签收且用户给出原因，申请执行写操作
status = pending
```

确认请求故意只有：

```json
{"userId":"alice","approved":true}
```

它不能重新传 `orderId` 或 `reason`。否则用户界面展示的是 ORD-1001，恶意或出错的客户端却可能在批准时换成 ORD-2002。`AgentService.confirm()` 只从数据库解析被冻结的 JSON，再执行同一工具和同一参数，这叫防止确认内容与执行内容发生 TOCTOU（检查时与使用时不一致）。

## 8. 为什么确认需要原子抢占

用户可能双击按钮，浏览器可能重试，请求也可能同时到达两个应用实例。它们访问的是同一张确认单，而不是同一个 Java 对象。

`claimConfirmation()` 执行的核心 SQL 是：

```sql
UPDATE agent_confirmation
SET status = 'executing'
WHERE id = ? AND user_id = ? AND status = 'pending';
```

只有一个请求能把 `pending` 改成 `executing` 并得到更新行数1。后来者更新行数0，收到 HTTP 409，因此远端退货申请只创建一次。这里防的不是线程看不见布尔值，而是跨线程、跨请求乃至跨实例的竞争，所以数据库条件更新比进程内 `AtomicBoolean` 更合适。

状态完整变化是：

```text
pending → executing → approved
                    ↘ failed
pending → denied
```

## 9. 三张 Agent 表怎样配合

| 表 | 这次保存的范围 | 写操作通路中的变化 |
| --- | --- | --- |
| `agent_session` | 整个开放任务的当前状态 | `running → waiting_confirmation → running → completed` |
| `agent_step` | 已经真正发生的决定/动作/结果 | 查询和加载手册立即写；写工具只有批准并执行后才写 |
| `agent_confirmation` | 一次尚待人决定的副作用操作 | 保存冻结参数，并记录 pending/approved/denied/failed |

注意：模型提出写工具时还没有创建对应 `AgentStep`，因为远端动作尚未发生。此时只有 `agent_confirmation`。批准成功后，真实 Observation 才被写成下一条 `AgentStep`；因此历史不会把“计划执行”误记成“已经执行”。

本课没有用一个数据库事务包住远端 HTTP 调用。数据库事务无法回滚另一个服务已经完成的退货申请；把网络调用放在长事务里还会长期占连接和锁。当前用确认状态与原子抢占保证同一确认不重复执行，但如果进程恰好在远端成功、落库前崩溃，仍需要远端幂等键才能做到生产级“恰好一次”。这是本课明确保留的边界。

## 10. 一条测试数据怎样走完整流程

测试目标：

```json
{
  "userId": "alice",
  "objective": "查询 ORD-1001，并为耳机不合适创建退货申请"
}
```

关键中间数据依次是：

1. `/api/system/health` 返回数据库可达、MCP 可达、发现2个工具；
2. `order_status({orderId: ORD-1001})` 返回 `delivered、签收3天、耳机`；
3. `load_skill({skillCode: return_request})` 返回手册，写工具从下一轮开始可见；
4. 模型提出 `return_request_create({orderId: ORD-1001, reason: 耳机不合适})`；
5. HTTP 响应是 `waiting_confirmation`，远端已创建数量仍为0；
6. Alice 批准确认，服务端读取冻结参数，远端返回申请编号 `RET-1001`；
7. Agent 再做一次 answer 决定，最终响应是 `completed`；
8. 对同一确认再次批准得到 HTTP 409，远端数量仍为1。

测试只脚本化“模型下一轮选择什么”。两个 HTTP 服务、MCP 消息、Spring、PostgreSQL、Flyway、确认竞争和远端计数都是真实执行，所以阅读时不需要钻进大型 Stub。

## 11. 健康检查与运行配置

主应用配置：

```properties
ragent.mcp.url=${RAGENT_MCP_URL:http://127.0.0.1:8091/mcp}
```

环境变量 `RAGENT_MCP_URL` 可以覆盖默认值。`GET /api/system/health` 会真实执行数据库 `SELECT 1` 和 MCP `tools/list`：全部可用返回 `UP`；已配置但不可达返回 `DEGRADED`，并在 `mcp.error` 给出原因。

测试不要求手动启动 MCP Server。`McpAgentApiLiveIT` 会在随机端口启动与生产相同的 `McpOrderServer` 类，并在结束时关闭；Testcontainers 继续自动准备临时 pgvector。

手工运行时需要三个终端：

```bash
# 终端1：数据库容器
docker compose up -d

# 终端2：独立 MCP 工具服务
mvn -q -DskipTests compile org.codehaus.mojo:exec-maven-plugin:3.5.1:java \
  -Dexec.mainClass=com.shitan.ai.mcp.McpOrderServerApplication

# 终端3：主应用
mvn spring-boot:run
```

当前 `pom.xml` 没有固定配置 `exec-maven-plugin`，所以上面故意写出完整插件坐标和版本；Maven 第一次执行时会下载这个运行插件。测试阶段优先绿色按钮，不要求先做三进程部署。

## 12. 本课边界

- MCP Server 使用真实 HTTP 和协议消息，但订单仍是内存教学数据，不冒充生产订单系统。
- MCP 工具在应用启动时发现一次；运行期间动态刷新目录暂不实现。
- Skill 只有一份本地 Markdown 手册，还没有后台管理和版本选择。
- 用户身份仍是教学请求中的 `userId`，尚未接登录鉴权；远端生产系统必须独立鉴权。
- 确认避免重复点击造成二次执行，但跨系统崩溃窗口要由远端幂等键继续解决。
- 不复制原项目的完整 MCP 注册中心、管理后台或多租户权限体系。

## 13. 代码阅读顺序

1. `McpAgentApiLiveIT.shouldDiscoverMcpToolsAndConfirmWriteWithFrozenArguments()`：先沿一个测试看健康、只读调用、Skill、等待确认、批准和重复批准的全部中间数据。
2. `McpOrderServer.listToolsResult()`：看外部服务怎样公开两个工具的名称、输入 Schema 和只读提示。
3. `McpToolClient.listTools()`：看客户端怎样发送 `tools/list`，再把远端 JSON 读成 `McpDiscoveredTool`。
4. `McpRemoteAgentTool`：看 Adapter 怎样让远端工具进入第19课已有的 `AgentTool` 接口。
5. `AgentService.availableToolDefinitions()` 和 `isSkillLoaded()`：看写工具为什么在手册加载前对模型不可见。
6. `SkillManualAgentTool.execute()` 与 `skills/return-request.md`：看 Skill 是怎样按需进入 Observation 的。
7. `AgentService.runLoop()`：看只读工具立即执行，写工具只冻结 `AgentConfirmation` 并返回。
8. `AgentController.confirm()` 与 `AgentService.confirm()`：看确认请求为什么没有业务参数，以及服务端怎样从数据库恢复被冻结参数。
9. `AgentRepository.claimConfirmation()` 与 V8 迁移：看数据库如何保证两个批准请求只有一个能执行。
10. `McpToolClient.callTool()` 与 `McpOrderServer.callTool()`：最后对照 `tools/call` 两端的请求、执行和内容块响应。
11. `SystemHealthService.health()`：看数据库和 MCP 的真实连通性怎样汇总成部署状态。
