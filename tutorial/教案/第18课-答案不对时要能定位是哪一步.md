# 第18课：答案不对时，要能定位是哪一步

## 先看三条业务通路

这一课位于“问答可观察性”层。它不改变检索算法或模型答案，而是在已有同步会话问答外面保存一份可检查的执行记录。

```text
问答通路：POST /api/questions
         → 创建 RagTraceRun
         → 依次执行并记录 memory / rewrite / intent / retrieve / generate 等节点
         → 保存 assistant 消息
         → Run 变为 completed
         → 返回答案、sources、runId、assistantMessageId

追踪通路：GET /api/rag-runs/{runId}?userId=alice
         → 校验 Run 属于 Alice
         → 读取 rag_trace_run + rag_trace_node + answer_feedback
         → 返回完整执行时间线

反馈通路：POST /api/rag-runs/{runId}/feedback
         → 校验 Run 已完成且属于当前用户
         → 用 Run 中的 assistantMessageId 关联真正回答
         → 保存或更新赞踩与原因
```

如果问答中途失败，已经完成的节点仍保留，当前节点记为 `failed`，整个 Run 也变成 `failed`。调用方可以用已有 `conversationId` 查询该会话最近的 Run。

## 1. 为什么只有 answer 和 sourceTitle 已经不够

前面的响应只能告诉用户最终答案和一个标题。现在问答已经包含会话改写、意图规划、多路召回、精排、模型路由和消息保存。答案不对时，单看最终文字无法区分下面几种情况：

- 追问被改写错了；
- 选错了知识库；
- 检索没有找到正确片段；
- 检索正确，但模型组织答案不理想；
- 回答已经生成，却在消息落库时失败。

因此这次引入两个层次：`Run` 代表一整轮问答，`Node` 代表 Run 中一个可单独观察的步骤。

## 2. 本课重要对象和职责

| 对象 | 代表的范围 | 主要职责 | 不负责什么 |
| --- | --- | --- | --- |
| `RagTraceRun` | 一轮父问题 | 保存用户、会话、总状态、最终消息编号和总错误 | 不保存每一步细节 |
| `RagTraceNode` | Run 中一个步骤 | 保存节点名、输入/输出摘要、耗时、状态和错误 | 不重新执行业务 |
| `RagTraceService` | 追踪编排 | 用 `recordNode` 包裹真实动作，并统一记录成功或失败 | 不理解 SQL，也不替代原业务 Service |
| `RagTraceRepository` | 三张观察表 | 执行 Run、Node、Feedback 的 JDBC 读写 | 不调用模型和检索 |
| `SourceReference` | 一份用户可查看的文档来源 | 把同一文档的多个 Chunk 合并，保留实际命中片段编号 | 不代替内部精排证据 |
| `AnswerFeedback` | 用户对一条回答的当前评价 | 用 runId 关联 assistant 消息，保存赞踩和原因 | 不自动判断模型正确性 |
| `RagTraceController` | 追踪和反馈 HTTP 边界 | 校验参数并调用追踪服务 | 不直接拼 SQL |

本课没有使用 AOP 注解自动拦截所有方法。当前只有一条同步会话链需要追踪，显式写出节点更容易看清真实顺序；等重复追踪代码真正大量出现后，才有理由考虑 AOP。

## 3. 成功问答的数据和状态怎样流动

真实测试问题是：`交通怎么报销，住宿标准是多少？`。检索最终选择同一文档中的两个 Chunk：

```text
RetrievedEvidence 1
  chunkId = 交通报销片段编号
  documentId = 差旅制度文档编号
  title = 差旅制度 / 交通报销

RetrievedEvidence 2
  chunkId = 住宿报销片段编号
  documentId = 同一个差旅制度文档编号
  title = 差旅制度 / 住宿报销
```

内部的 `evidence` 仍保留两条，因为模型确实看了两个片段。面向用户的 `sources` 按 `documentId` 分组，因此只返回一条：

```json
{
  "sourceId": "文档编号",
  "title": "差旅制度 / 交通报销",
  "preview": "高铁二等座可以凭电子票报销……",
  "chunkIds": ["交通片段编号", "住宿片段编号"]
}
```

这里 `sourceId` 不是新生成的临时序号，而是已有 `knowledge_document.id`。Chunk 排名变化时，只要来源仍是同一文档，用户看到的来源编号就保持稳定。

一次成功 Run 的实际节点顺序如下：

```text
running
  ├─ memory_load              读取摘要和近期消息
  ├─ user_message_save        保存用户问题
  ├─ model_tier               解析模型档位
  ├─ rewrite_question         把追问改写成独立问题
  ├─ intent_plan              拆问并决定知识库作用域
  ├─ retrieve_1               Embedding、多通道召回、RRF、Rerank
  ├─ generate_1               使用证据调用答案模型
  ├─ assistant_message_save   保存最终回答，得到 messageId
  └─ memory_compact           检查是否需要滚动摘要
completed
```

如果规划出多个子问题，就会出现 `retrieve_1/generate_1`、`retrieve_2/generate_2`。数字表示第几个子问题，不表示第几个模型候选。

## 4. `recordNode` 为什么接收函数

`RagTraceService.recordNode(...)` 接收的 `TraceOperation<T>` 不是业务结果，而是一段“稍后由追踪服务执行的动作”。它的执行顺序是：

```text
记录开始时间
→ operation.execute() 执行原业务
→ 成功：保存 completed、输出摘要、耗时，返回原结果
→ 失败：保存 failed、错误、耗时，再把原异常抛回上层
```

泛型 `T` 表示每个步骤可以有不同结果：加载记忆得到 `ConversationMemory`，规划得到 `List<IntentPlan>`，保存消息得到 `Long`。`Function<T, String>` 只负责把结果压缩成短摘要，不改变原结果。

这种写法让业务结果继续交给下游，不需要为了追踪把所有结果改成统一的大对象。它也保证追踪不能吞掉异常：节点保存失败信息后，原来的 404、网络异常等仍按原业务语义返回。

## 5. 失败时怎样定位

测试在已有会话中故意传入不存在的知识库 `missing-knowledge-base`。结果是：

```text
memory_load          completed
user_message_save    completed
model_tier           completed
rewrite_question     completed
intent_plan          failed：知识库不存在
```

Run 最终为 `failed`，`assistantMessageId=null`，因为系统根本没有生成和保存回答。HTTP 仍返回原来的 404，而不是被追踪功能改成另一种错误。

失败响应没有成功响应里的 `runId`，但调用方仍知道原会话编号，所以可以查询：

```text
GET /api/rag-runs/latest?conversationId=...&userId=alice
```

这次可以明确判断：会话读取和问题改写都成功，错误发生在意图规划检查知识库编号时；没有必要去怀疑向量检索或答案模型。

## 6. 三张新表分别保存什么

Flyway V6 创建三张表：

| 表 | 何时写入 | 保存内容 |
| --- | --- | --- |
| `rag_trace_run` | 问答开始、成功或失败时 | 一轮问答的总状态、会话、用户、问题摘要、回答消息编号、错误 |
| `rag_trace_node` | 每个步骤结束或失败时 | 节点名、输入/输出摘要、耗时、状态、错误 |
| `answer_feedback` | 用户点赞或点踩时 | runId、assistantMessageId、userId、rating、原因 |

问答过程中还会访问既有表：

- `conversation_session`：确认会话所有者；
- `conversation_message`：写 user 和 assistant 消息；
- `knowledge_base`：规划时检查知识库；
- `knowledge_document`、`knowledge_chunk`：检索证据；
- `conversation_summary`：读取或更新摘要。

这次没有把整轮问答放进一个大事务。每个 Trace 节点和原业务动作各自提交：这样后面的模型调用失败时，前面已经保存的诊断信息不会随着一个大事务全部回滚。代价是应用突然断电时可能留下 `running` Run；生产系统以后需要超时扫描，本课不提前加入定时任务。

## 7. `getLong()` 为什么会把 SQL NULL 读成 0

JDBC 的 `ResultSet.getLong(...)` 返回 Java 基本类型 `long`，而基本类型不能是 `null`。数据库列为空时，它先返回 `0`，调用方必须紧接着调用 `resultSet.wasNull()` 才知道刚才的0究竟是真值还是 SQL NULL。

本课第一次真实测试暴露了这个细节：失败 Run 本应没有回答消息，JSON 却显示 `assistantMessageId=0`。修复后读取顺序是：

```java
long messageId = resultSet.getLong("assistant_message_id");
boolean messageIdWasNull = resultSet.wasNull();
```

之后再读取其他列。`wasNull()` 只描述“最近一次 getter”，如果中间又调用了 `getString()`，它就不再对应 `assistant_message_id`。

## 8. 为什么 Trace 只保存摘要

节点输入输出最多保存500个字符，并压平多余空白。当前不会把完整文档、全部 Prompt、API Key 或长模型回答复制进 Trace。原因有三个：

- Trace 表不能无限膨胀；
- 企业文档和用户问题可能包含敏感信息；
- 定位阶段通常只需要作用域、数量、标题、状态和耗时。

这只是教学项目的第一道边界，不等于完整生产脱敏。生产系统还要对身份证号、手机号、密钥格式等做专门屏蔽，并设置保存期限。

## 9. 本课明确边界

- 当前只追踪带 `userId` 的同步会话问答；旧的无会话入口和 SSE 暂不改造。
- `retrieve_n` 内部包含 Embedding、向量/关键词召回、RRF 和 Rerank；本课能区分“检索阶段”和“生成阶段”，还没有把检索内部每个小步骤分别落库。
- Feedback 只保存当前评价，再次提交会覆盖同一 Run 的旧评价；不保留反馈修改历史。
- Trace 是业务诊断记录，不是分布式链路追踪标准，也没有引入 OpenTelemetry。

## 10. 代码阅读顺序

1. `RagObservabilityApiLiveIT.shouldExposeSourcesTraceFeedbackAndFailedNode()`：先用一条完整测试认识最终要观察的来源、成功 Run、反馈和失败 Run。
2. `V6__create_rag_observability.sql`：看三张新表怎样分别关联会话、消息和 Run。
3. `ConversationQuestionService.ask()`：看最外层怎样创建 Run、按顺序记录节点并完成或失败收尾。
4. `IntentRoutingService.answer(..., runId)`：看改写、规划和子问题编号如何进入追踪。
5. `BailianRagAssistant.answerFromDatabase(..., runId, subQuestionNumber)`：看检索与生成为什么分成两个节点。
6. `RagTraceService.recordNode()`：理解函数参数、泛型结果、计时、成功记录和失败重抛。
7. `RagTraceRepository`：结合 SQL 表理解每种状态最终写到哪里，特别留意 `getLong + wasNull`。
8. `RetrievedEvidence`、`SourceReference` 和 `QuestionResponse`：最后比较内部 Chunk 证据、用户文档来源和 HTTP 最终包装的范围。
9. `RagTraceController`：看追踪查询、最近失败查询和反馈入口。
