# 第19课：开放任务不能再靠固定步骤写死

## 先看三条业务通路

这一课位于“任务决策层”。前面的 RAG 管线仍然负责固定知识问答；新的 Agent 入口负责面对一个开放目标，根据刚拿到的中间结果决定下一步做什么。

```text
首次任务：POST /api/agent/tasks
         → AgentService 创建会话
         → 决策模型选择 knowledge_search
         → 知识工具调用已有 RAG，得到7天政策 Observation
         → 决策模型选择 order_lookup
         → 订单工具返回签收3天 Observation
         → 决策模型选择 answer
         → 会话和每一步保存在 PostgreSQL，最终回答交给 HTTP 调用方

恢复任务：POST /api/agent/tasks（带旧 sessionId）
         → 从 PostgreSQL 恢复旧 Scope 和全部步骤
         → 使用新目标继续决定、调用工具、保存 Observation
         → 步骤编号接着旧编号增长，不覆盖历史

防失控：模型一直选择 tool
       → AgentService 最多允许本轮作出4次决定
       → 停止继续调用模型和工具
       → 会话保存为 limit_reached，并返回明确收尾文字
```

最重要的变化是：以前 Java 预先写死了“改写 → 规划 → 检索 → 生成”的顺序；现在 Java 只写循环规则、工具边界和停止条件，循环中“下一步选哪个工具，还是已经可以回答”由决策模型根据 Observation 决定。

## 1. 为什么前面的固定 RAG 不够

`POST /api/questions` 很适合知识问答，因为所有问题都沿着确定步骤处理。即使第14课把父问题拆成多个子问题，Java 仍然预先知道每个子问题都要检索并生成答案。

这次需求是：

> 先查退货政策，再查订单 ORD-1001；结合政策和订单状态，判断能否退货。

这个目标需要两类事实：政策来自知识库，签收天数来自订单系统。如果以后目标变成“订单不存在就向用户索要正确编号”，需要做的下一步又会随中间结果改变。继续在 Java 中堆 `if/else`，实际上是在手写越来越大的任务流程图。

因此本课新增 Agent 入口，但没有删除原 RAG：

- 固定、稳定、需要强确定性的知识问答继续走 `/api/questions`；
- 步骤无法预先完全确定的开放任务走 `/api/agent/tasks`；
- 已经成熟的 RAG 被包装为 `knowledge_search` 工具，成为 Agent 可以选择的一项能力。

Agent 不是“更高级所以替换一切”。动态决策会增加模型调用、成本和不可预测性；能用固定流程清楚解决的问题，固定流程仍然更合适。

## 2. 核心执行链：哪个对象把什么交给谁

```text
AgentController
  接收 userId、objective、knowledgeBaseId/sessionId
          │
          ▼
AgentService
  创建/恢复 AgentSession，加载 AgentStep，建立 AgentScope
          │
          ▼
AgentDecisionModel（生产环境是 BailianAgentDecisionModel）
  阅读目标 + 工具说明 + 历史 Observation
  返回一个 AgentDecision：tool 或 answer
          │
          ├── tool ──► AgentService 按白名单找到 AgentTool
          │              ├─ KnowledgeSearchAgentTool → 已有 BailianRagAssistant
          │              └─ OrderLookupAgentTool     → 本地只读订单数据
          │                         │
          │                         ▼
          │                    Observation
          │                         │
          │                         └── 保存 AgentStep，再回到决策模型
          │
          └── answer ─► 保存最终 AgentStep
                        AgentSession 变为 completed
                        返回 AgentResponse
```

本课的重要职责如下：

| 对象 | 接到什么 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| `AgentController` | HTTP JSON | 暴露创建/恢复任务和查询会话入口 | 不决定工具，不写 SQL |
| `AgentService` | 任务请求 | 控制循环、执行白名单工具、持久化步骤、限制迭代 | 不理解退货政策，不自己生成答案 |
| `AgentDecisionModel` | Scope、历史步骤、工具说明 | 只选择下一次 `tool` 或 `answer` | 不直接碰数据库、订单或知识库 |
| `KnowledgeSearchAgentTool` | `question` 和服务端 Scope | 复用已有 RAG 查询指定知识库 | 不允许模型自己换知识库 |
| `OrderLookupAgentTool` | `orderId` | 返回教学订单的只读快照 | 不退款，不修改订单 |
| `AgentRepository` | 会话和步骤对象 | 读写 `agent_session`、`agent_step` | 不参与模型判断 |

## 3. ReAct 到底是什么，本课保存了什么

ReAct 可以先直白理解成重复下面三件事：

```text
根据目标和已有结果决定下一动作
→ 执行动作
→ 观察动作结果，再决定下一动作
```

正式资料常写成 `Reasoning → Action → Observation`。本课没有要求模型输出或保存冗长的隐藏思维过程，而只保存一句可展示的 `decisionSummary`。例如：

```json
{
  "type": "tool",
  "decisionSummary": "已有政策，还需要 ORD-1001 的真实签收天数",
  "toolName": "order_lookup",
  "arguments": {"orderId": "ORD-1001"}
}
```

这里几组词需要分清：

- `Decision` 是模型这一次只选择一个动作的结构化结果。
- `Tool` 是 Java 允许 Agent 使用的一项受控能力，不等于任意执行 Java 方法。
- `Action` 在本课具体表现为调用一个 Tool。
- `Observation` 是 Tool 执行后的文字结果，它会进入下一次模型输入。
- `decisionSummary` 是简短、可展示的选择说明，不是要求模型公开内部思维链。

## 4. 一条真实测试数据怎样在循环中变化

测试输入是：

```json
{
  "userId": "alice",
  "objective": "先查退货政策，再查订单 ORD-1001，判断能不能退货",
  "knowledgeBaseId": "售后政策知识库编号"
}
```

### 第一次决定

此时历史步骤为空。决策结果是：

```json
{
  "type": "tool",
  "toolName": "knowledge_search",
  "arguments": {"question": "商品签收后多少天可以无理由退货？"}
}
```

`KnowledgeSearchAgentTool` 不重新实现检索，而是把问题和 `AgentScope.knowledgeBaseId` 交给已有 `BailianRagAssistant`。它真实完成 Embedding、数据库检索、精排和回答，返回：

```text
知识回答：商品签收后 7 天内可以无理由退货。；来源：退货政策
```

这段文字就是第一次 `Observation`，保存到 `agent_step.observation`。

### 第二次决定

模型现在既看到原目标，也看到7天政策，于是选择：

```json
{
  "type": "tool",
  "toolName": "order_lookup",
  "arguments": {"orderId": "ORD-1001"}
}
```

订单工具返回：

```text
订单号=ORD-1001，状态=delivered，签收天数=3，商品=耳机
```

### 第三次决定

政策和订单事实都已经齐全，这一次返回 `answer` 而不是继续调用工具：

```json
{
  "type": "answer",
  "answer": "ORD-1001 已签收3天，仍在7天期限内，可以申请无理由退货。"
}
```

所以状态变化是：

```text
agent_session.status = running
  → step 1: tool / knowledge_search / 7天政策
  → step 2: tool / order_lookup / 签收3天
  → step 3: answer / 最终回答
agent_session.status = completed
```

## 5. 模型在生产环境究竟收到了什么

`BailianAgentDecisionModel` 会把输入分成两条 Chat Completions 消息。

第一条 `system` 说明边界和输出格式，大意是：每次只能选择一个动作；工具调用只能输出指定 JSON；已有 Observation 足够时返回 answer JSON；不能假装执行过工具。

第二条 `user` 是当前状态，形状如下：

```text
目标=先查退货政策，再查订单 ORD-1001，判断能不能退货
工具=[
  {"name":"knowledge_search","description":"...","argumentNames":["question"]},
  {"name":"order_lookup","description":"...","argumentNames":["orderId"]}
]
历史步骤=[
  {
    "iteration":1,
    "decisionType":"tool",
    "toolName":"knowledge_search",
    "toolInput":"{...}",
    "observation":"知识回答：商品签收后 7 天内..."
  }
]
```

模型输出仍然只是文本，但我们要求这段文本长得像 JSON。Jackson 的工作分为两步：

1. `readTree(...)` 把 JSON 文本解析成可按字段读取的 `JsonNode` 树；
2. Java 读取 `type/toolName/arguments/answer`，校验后构造 `AgentDecision`。

这个 JSON 不是百炼额外规定的 Agent 协议，而是本项目写在 Prompt 里的应用层约定。远端模型负责按约定生成，Java 必须继续校验，不能因为文字来自模型就直接信任。

## 6. 为什么模型给了 toolName，Java 还要再查白名单

模型只能“建议调用 `order_lookup`”，不能直接执行它。`AgentService` 会在 Spring 已经注入的 `List<AgentTool>` 中，按稳定名称建立 `Map<String, AgentTool>`。执行时只有 Map 中真实存在的名称才能被调用。

这样可以防止两类问题：

- 模型写错或编造 `delete_all_orders`，Java 找不到工具，只把“工具不存在或未授权”作为 Observation；
- 模型尝试把知识库编号塞进工具参数，`KnowledgeSearchAgentTool` 仍只使用服务端保存的 `AgentScope.knowledgeBaseId`。

`Tool Schema` 中的 Schema 在这里指“给模型阅读的工具结构说明”，当前包含名称、用途和允许的参数名。它帮助模型正确组装 Action，但不代替 Java 权限检查。

## 7. `AgentScope` 和几个数据类怎样分工

这几个对象字段看起来有重合，但它们处在不同阶段：

| 数据类 | 代表的范围 | 特有内容 | 谁产生、谁消费 |
| --- | --- | --- | --- |
| `AgentRequest` | 一次 HTTP 请求 | 用户输入的 objective、可选 sessionId | Controller 接收，Service 消费 |
| `AgentSession` | 可跨请求恢复的一次 Agent 会话 | 所有者、最新目标、知识库边界、总状态 | Repository 从 `agent_session` 读出 |
| `AgentScope` | 当前这一轮不可变的服务端执行边界 | 已确认的用户、知识库、最大迭代、旧步骤 | Service 建立，模型和工具读取 |
| `AgentDecision` | 模型的一次选择 | tool/answer 分支、工具参数或答案 | DecisionModel 产生，Service 消费 |
| `AgentStep` | 已经发生且已落库的一次迭代 | iteration、工具输入、Observation | Repository 保存并恢复 |
| `AgentResponse` | HTTP 最终包装 | 会话状态、当前答案、全部步骤 | Service 组装，Controller 返回 |

`Scope` 日常有“范围”的意思。这里它回答的是：这个 Agent 会话属于谁、允许查哪个知识库、本轮最多决定几次、从数据库恢复了哪些历史。它不是模型可以随意改写的参数袋。

## 8. 恢复会话不是把旧答案字符串塞回去

首次请求创建 `agent_session`，每次决定写一行 `agent_step`。追问：

```json
{
  "userId": "alice",
  "objective": "那 ORD-1002 呢？",
  "sessionId": "旧会话编号"
}
```

服务端会先用 `sessionId + userId` 找旧会话，防止 Alice 恢复 Bob 的任务。请求没有重复传 `knowledgeBaseId` 时，继续使用数据库中原来保存的知识库边界；然后恢复全部旧步骤。

旧步骤最大编号为3，所以新一轮从4开始：

```text
iteration 4：order_lookup(ORD-1002)
Observation：签收12天

iteration 5：answer
最终回答：超过7天，需要人工审核
```

这和第13课的对话记忆相关但不相同：对话记忆主要帮助固定 RAG 理解省略追问；Agent 会话保存的是工具动作和 Observation，目的是让动态任务能够继续决策。

## 9. 为什么必须由 Java 控制最大迭代次数

如果模型每次都回答“再查一次订单”，循环会持续消耗时间、线程、模型额度，甚至重复调用有副作用的工具。不能让同一个负责决策的模型同时决定自己何时必须停止。

`AgentService` 每次 HTTP 调用最多执行 `ragent.agent.max-iterations=4` 次决定。四次都没有得到 answer 时：

```text
status = limit_reached
answer = 任务在 4 次决定内没有完成，请缩小目标或补充信息。
```

注意这是“每次 HTTP 调用的决定数上限”，不是整段会话永久只能有4个步骤。恢复旧会话后，新的一轮又有自己的4次额度，步骤编号则继续累计。

## 10. 两张新表怎样参与每一条通路

Flyway V7 新增：

| 表 | 保存什么 |
| --- | --- |
| `agent_session` | 会话所有者、最新目标、知识库边界、running/completed/limit_reached/failed 和最终回答 |
| `agent_step` | 每次决定的编号、类型、摘要、工具名、工具 JSON 参数和 Observation |

首次任务的数据库顺序是：

```text
INSERT agent_session(running)
→ INSERT agent_step(tool: knowledge_search)
→ INSERT agent_step(tool: order_lookup)
→ INSERT agent_step(answer)
→ UPDATE agent_session(completed, final_answer)
```

恢复任务的顺序是：

```text
SELECT agent_session（同时检查 userId）
→ SELECT agent_step（恢复历史）
→ UPDATE agent_session(running, latest_objective)
→ INSERT 后续 agent_step
→ UPDATE agent_session(completed)
```

本课没有在 `AgentService.run()` 上添加一个覆盖网络调用和整个循环的大事务。每条 JDBC 写入独立提交，因此模型或后续工具失败时，前面已经发生的 Observation 不会全部回滚，排错和恢复更容易。代价是进程突然断电时可能留下 `running` 会话；生产系统可以以后根据真实需求增加超时接管，本课不提前加定时扫描。

## 11. 为什么测试只脚本化“决策模型”

测试要稳定验证固定顺序：先知识、再订单、最后回答，以及追问和迭代上限。真实模型每次可能用略有不同的措辞或选择顺序，如果直接用它决定步骤，业务正确也可能偶发红灯。

因此 `ScriptedDecisionConfiguration` 只替换 `AgentDecisionModel`：

- HTTP、Spring、PostgreSQL、Flyway 和两张 Agent 表都是真实的；
- 文件上传、文档解析、Embedding、pgvector 检索和知识回答都是真实的；
- 订单工具也执行真实 Java 实现；
- 只有“下一步选什么”使用可预测脚本。

这个脚本不伪造工具结果。它仍然必须读到已经保存的步骤，才能从知识工具转向订单工具。这样测试清楚保护 Agent 循环本身，又不会堆出一套难读的大型 HTTP Stub。

正常启动应用时，`@Primary` 测试 Bean 不存在，Spring 使用真正的 `BailianAgentDecisionModel`。

## 12. 本课边界

- 两个工具都是只读的；退款、取消订单等写操作尚未开放。
- 订单数据暂时是内存中的两个教学快照，不冒充真实订单系统。
- Tool Schema 只是当前最小说明，还没有接入跨进程工具发现协议。
- 工具异常会变成 Observation，让模型有机会修正；决策模型本身异常会把会话标成 `failed`。
- 本课响应是一次性 JSON，不增加 Agent SSE 流式事件。
- 下一课以前不实现 MCP、写操作确认或 Skill 手册。

## 13. 容易混淆的三种“步骤”：它们不是一层包一层

这一课最容易产生的误解，是把以前见过的 `IngestionNode`、`RagTraceNode` 和现在的 `AgentStep` 连成“问答 → Node → Trace Node → Agent Step”。真实关系并不是包装，而是三条不同通路各自记录自己的步骤：

```text
文档摄取通路：IngestionNode
  fetch → parse → embedding → publish
  它是可执行节点，输入和输出是 IngestionContext。

固定 RAG 观测通路：RagTraceNode
  memory_load → rewrite → intent_plan → retrieve_1 → generate_1
  它是一次 RAG Run 的观测记录，不是拿来执行的 Node 对象。

Agent 动态任务通路：AgentStep
  knowledge_search → order_lookup → answer
  它记录 Agent 每一轮选择、工具输入和 Observation。
```

因此，“Node”这个单词在两个类名里也不代表同一种东西。`IngestionNode` 是会被 Runner 调用的处理器；`RagTraceNode` 是数据库里的一行时间线数据。`AgentStep` 则属于另一个更外层的动态任务循环。

还有一个非常重要的事实：当前 `KnowledgeSearchAgentTool` 直接调用 `BailianRagAssistant.answerFromDatabase(...)`，而且没有传入 `runId`，所以这条 Agent 工具通路不会生成第18课的 `RagTraceNode`。它复用了单个子问题的 RAG 核心，但没有把第18课完整的固定问答编排再包进去。

## 14. 按“任务 → 问题 → 子问题”重新看两条路线

固定问答路线和 Agent 路线不是完全包含关系，而是在最深处复用了同一个单子问题 RAG 核心：

```text
固定 /api/questions 路线
父问题
  → ConversationQuestionService 加载对话、改写
  → IntentRoutingService / IntentPlanner 拆成一个或多个子问题和 Plan
  → 每个子问题调用 BailianRagAssistant
  → 聚合子答案
  → QuestionResponse

动态 /api/agent/tasks 路线
开放任务 objective
  → AgentService 多轮决策
  → 某一轮选择 knowledge_search
  → 工具把一个已经聚焦的问题直接交给 BailianRagAssistant
  → Observation 回到 Agent 历史
  → Agent 再决定调用别的工具还是回答
```

`KnowledgeSearchAgentTool` 没有调用 `ConversationQuestionService`，也没有重新做问题改写、拆分和 Plan，是有意的。Agent 自己已经是外层规划者；如果再把一个完整规划器套进去，就会出现“外层 Agent 拆任务、内层固定问答又拆一次”的重复规划，谁负责决定子问题也会变得含糊。

所以当前约定是：Agent 决定需要查两个不同知识问题时，就分两轮调用 `knowledge_search`；每次工具调用只负责一个已经聚焦的子问题。固定 `/api/questions` 则继续适合“用户给出一个父问题，由系统自动改写、拆分、路由和聚合”的场景。

## 15. 为什么工具已经有参数，还需要 AgentScope

工具参数和 `AgentScope` 的可信程度不同：

| 数据 | 谁决定 | 例子 | 能否直接决定安全边界 |
| --- | --- | --- | --- |
| 工具参数 | 模型在本轮生成 | `question`、`orderId` | 不能，模型可能写错、越界或编造 |
| `AgentScope` | 服务端从请求和数据库确认 | `userId`、知识库边界、sessionId、迭代上限、旧步骤 | 可以，工具必须服从它 |

例如 `knowledge_search` 的参数只让模型给出 `question`，真正使用哪个知识库来自 `scope.knowledgeBaseId()`。即使模型偷偷在参数里加一个别人的知识库编号，工具也不会采用。可以把它理解成：参数告诉工具“这次想做什么”，Scope 告诉工具“你代表谁、只能在哪个范围内做”。

## 16. Agent history 与 conversation memory 有什么区别

它们都保存过去，但服务于不同的下一步：

| 名称 | 主要保存 | 下一位读者 | 用途 |
| --- | --- | --- | --- |
| Conversation memory | 用户消息、助手自然语言回答、历史摘要 | 固定 RAG 的问题改写过程 | 理解“它”“那怎么办”等省略追问 |
| Agent history | 决策、工具名、工具参数、Observation、最终答案 | Agent 决策模型 | 判断工具已经做过什么、还缺哪项事实 |

例如“那 ORD-1002 呢”需要 conversation memory 帮助理解“那”；而“政策已经查到7天，但还没查订单状态”需要 Agent history 帮助决定下一工具。二者可以在未来某条真实需求中协作，但现在不应因为都叫历史就合并。

## 17. Agent session 与 conversation session 有什么区别

`conversation session` 管的是一段自然语言对话及摘要水位；`agent session` 管的是一个目标、动态工具步骤、等待状态和迭代上限。它们也不是谁包装谁，而是两个状态机：

```text
conversation session：消息不断追加 → 过长时生成摘要 → 继续对话
agent session：running → completed / limit_reached / failed
```

分开以后，普通聊天不必承担工具执行状态；Agent 任务恢复时也能准确知道哪些工具已经执行，而不是从一串自然语言里猜测。

## 18. 为什么每保存一步都重新 findSteps

`insertStep(...)` 当前只负责写入，没有返回数据库最终保存的 `AgentStep`。数据库会补上真实主键和创建时间。因此保存后重新执行 `findSteps(sessionId)` 有三个直接好处：

1. 下一轮看到的历史带有真实 `id` 和 `createdAt`，不是 Java 临时拼出的半成品；
2. 首次执行与服务重启后的恢复都使用同一种历史形状；
3. 数据库成为可恢复状态的唯一事实来源，不会同时维护一份容易漏同步的内存列表。

这不是性能最高的办法，但在当前数据量和教学阶段更直白。以后真的出现步骤很多、整表回读成为性能问题时，可以让 `insertStep` 返回已保存行，再只把这一行追加到内存历史；现在不提前优化。

## 19. 代码阅读顺序

1. `AgentApiLiveIT.shouldRunResumeAndLimitAgentLoop()`：先看真实测试输入、三步结果、恢复后的第4/5步和四次迭代上限。
2. `AgentController.run()`：看新的 HTTP 入口只把请求交给 Agent 服务。
3. `AgentRequest`、`AgentSession`、`AgentScope`、`AgentDecision`、`AgentStep`、`AgentResponse`：结合第7节的表，分清请求、数据库会话、执行边界、单次决定、历史步骤和最终响应。
4. `AgentService.run()`：沿 `for` 循环看“决定 → tool/answer 分支 → 保存 → 下一轮”。
5. `AgentService.openSession()`：看新建、按 userId 恢复、继承知识库边界和步骤续号。
6. `AgentTool`、`AgentToolDefinition`：看模型能阅读的说明与 Java 能执行的能力怎样分开。
7. `KnowledgeSearchAgentTool.execute()`、`OrderLookupAgentTool.execute()`：比较复用真实 RAG 的工具和本地只读工具。
8. `BailianAgentDecisionModel.decide()`：看模型输入怎样由目标、工具和 Observation 组成。
9. `BailianAgentDecisionModel.parseDecision()`：看 Jackson 如何把模型 JSON 变成受校验的 `AgentDecision`。
10. `AgentRepository` 和 `V7__create_agent_sessions.sql`：最后把运行状态对应到两张表和 SQL 顺序。
