 # 第 16 课：一个模型服务不稳定时，问答不能整体失效

## 先看本课在整条问答链的哪一层

前几课已经把问题处理成了“父问题 → 子问题 → 作用域 → 多通道证据 → 答案”。本课不再改变会话、拆问和检索，而是只替换最深处“证据交给哪个 Chat 模型生成答案”这一层。

```text
QuestionResponse
  → RoutedKnowledgeAnswer：聚合多个子问题
  → KnowledgeAnswer：一个子问题的证据和回答
  → ModelRoutingService：按 fast/standard/deep 选择候选
       ├─ 首选模型成功：返回答案，状态 CLOSED
       ├─ 首选模型空响应/异常：标记 OPEN，尝试备用模型
       └─ 冷却后：放行一次 HALF_OPEN 探测，成功则恢复 CLOSED
  → BailianChatModelInvoker
  → BailianClient：按指定 model 组装 Chat Completions JSON
```

一句话概括：前面的检索证据不变，只让“最后生成答案的模型”拥有候选、档位和故障切换能力；模型失败时不能重新检索，也不能重复生成已经成功返回的正文。

## 为什么现在必须引入模型路由

目前 `BailianClient` 直接写死 `qwen-plus-latest`。这在单模型时很简单，但出现以下需求后就不够了：

- 快速问答希望用速度更快的模型；复杂问题希望用能力更强的模型。
- 外部模型可能超时、限流、返回空正文或服务暂时不可用。
- 如果每次失败都继续撞同一个模型，整个请求链会变慢，故障也会扩大。

本课只解决同步答案生成，不改造第 7 课已经完成的 SSE 取消机制，也不同时为 Embedding、精排和摘要建立多套路由。需求先落在最明确的一个位置：最终答案 Chat 调用。

## 完整执行链和对象职责

1. `QuestionRequest.modelTier` 是可选的业务档位文字：`fast`、`standard` 或 `deep`。不传或写错时统一使用 `standard`。
2. `ConversationQuestionService` 把档位传给 `IntentRoutingService`；会话记忆和模型选择是两件事，不能把档位存进历史摘要。
3. `IntentRoutingService` 继续负责拆问和知识库作用域，只把同一个档位交给每个子问题的 `BailianRagAssistant`。
4. `BailianRagAssistant` 已经拿到 `KnowledgeAnswer` 所需的最终证据，现在把答案生成交给 `ModelRoutingService`。
5. `ModelRoutingService` 先把请求档位相同的候选排在前面，再按 priority 尝试；调用成功就结束，调用异常就标记该候选为 `OPEN` 并继续。
6. `ManagedChatModel` 为每个模型保存自己的状态。`CLOSED` 表示正常，`OPEN` 表示暂时跳过，`HALF_OPEN` 表示冷却结束后只允许一个探测请求。
7. `BailianChatModelInvoker` 只负责把“模型名 + 问题 + 证据”交给 `BailianClient`。路由层不再知道百炼 URL、Authorization 或 Jackson。
8. `BailianClient.generateAnswer(..., model)` 只把以前写死的模型常量改成调用方传入的模型名，Prompt 和证据边界不变。

```text
证据已经准备好
       ↓
请求档位：standard
       ↓
primary qwen-plus-latest ──失败──→ OPEN
       │成功                         ↓
       └──────────────→ 返回答案   backup candidate
                                      ↓
                         成功 → CLOSED，返回答案
                         失败 → 继续下一个候选
```

## 本课新增的数据类和它们的位置

| 对象 | 处在哪一层 | 保存什么 | 不负责什么 |
|---|---|---|---|
| `ModelTier` | 请求语义层 | fast/standard/deep 三种业务档位 | 不等于供应商模型名 |
| `ManagedChatModel` | 候选状态层 | 模型名、档位、优先级、失败状态和冷却时间 | 不发送 HTTP |
| `ModelHealthState` | 熔断状态层 | CLOSED、OPEN、HALF_OPEN | 不保存回答正文 |
| `ChatModelInvoker` | 调用契约层 | “指定模型生成答案”的最小函数约定 | 不决定选哪个模型 |
| `ModelRoutingService` | 路由编排层 | 候选排序、失败切换、健康状态变化 | 不组装 JSON |
| `BailianChatModelInvoker` | 供应商适配层 | 把通用调用转成百炼客户端调用 | 不做熔断判断 |

这和前面数据类的层次是同一种思路：`RetrievedEvidence` 描述检索阶段的一条证据，`KnowledgeAnswer` 描述一个子问题的答案；本课的 `ManagedChatModel` 描述模型候选的状态。它们都不是数据库表行，而是运行过程中的阶段快照。

## 三态健康状态到底防止什么

### CLOSED：正常尝试

模型没有被发现故障，每个请求都可以尝试它。成功后失败计数清零。

### OPEN：暂时隔离

一次调用失败后，本课先把候选隔离两秒。隔离期间的新请求直接跳过它，避免每个请求都等待同一个已经失败的服务。

### HALF_OPEN：只做一次恢复探测

冷却结束后不能让几十个请求同时撞向故障模型，所以只放行一个探测。探测成功回到 `CLOSED`，失败则重新进入 `OPEN`。

这里的状态是“每个模型候选独立拥有”的，不是所有请求共享一个答案。多个请求可能同时读取同一个候选状态，所以状态转换使用 `synchronized` 和原子计数保护。

## `ModelTier` 和真实模型名为什么分开

业务只应该说“这个请求需要 fast”或“需要 deep”，不应该把 `qwen-plus-latest` 写进 Controller。模型名属于部署配置，当前格式为：

```text
fast=qwen-turbo-latest,standard=qwen-plus-latest,deep=qwen-max-latest
```

通过 `ragent.chat-models` 配置。默认只启用已经验证过的 `standard=qwen-plus-latest`，不会凭空启用你账户里可能没有权限的模型。只有你确认百炼账户可以调用其他模型时，才在 VS Code 的 `application.properties` 或启动参数中增加候选。

本课中的 `fast/standard/deep` 是我们自己的业务语言；供应商模型名是实现配置，两者不能混为一谈。

## 测试怎样观察故障切换

打开 [ModelRoutingTest.java]，它没有伪造 HTTP 响应，而是给路由器一个很小的“模型调用函数”：

```text
primary 第一次调用抛出 IOException
backup 返回“备用模型回答”
```

第一次请求观察：

```text
primary → 失败 → OPEN
backup  → 成功 → CLOSED
```

第二次请求观察：

```text
primary 被跳过
backup 继续成功
```

测试断言 `primaryCalls == 1`，它保护的不是某个实现细节，而是“已经隔离的模型不能被每个新请求重复撞击”。另一个测试让 `fast` 请求优先选择 fast 候选，说明业务档位和优先级确实影响选择。

现有的 `ConversationQuestionApiLiveIT` 仍然会真实经过 `ModelRoutingService`，默认配置只有 standard 候选，所以不会改变已验证的百炼路径。配置多个真实候选后，才需要再增加真实故障切换验收；不建议为了制造故障而反复调用不存在的模型。

## 配置方法

当前默认配置不需要改动，继续使用已经永久配置好的 `DASHSCOPE_API_KEY`。如果百炼账户确认有多个模型，可以在：

[application.properties](/home/shitanli/ln_rebuild/ragent/ragent-st/src/main/resources/application.properties:1)

增加：

```properties
ragent.chat-models=fast=qwen-turbo-latest,standard=qwen-plus-latest,deep=qwen-max-latest
```

不要把 API Key 写进这个文件。只配置模型名称即可。模型不可用时，应用请求会按本课的候选切换规则尝试其他健康候选；如果所有候选都不可用，才返回错误。

## 代码阅读顺序

1. 先看 [ModelRoutingTest.java]，看 primary 失败、backup 成功以及两次调用后的状态。
2. 看 [QuestionRequest.java]，确认 `modelTier` 只是可选请求字段。
3. 看 [ConversationQuestionService.java] 和 [IntentRoutingService.java]，确认档位如何沿父问题、子问题继续传递。
4. 看 [BailianRagAssistant.java] 的 `answerFromDatabase`，确认检索证据已经准备好后才进入模型路由。
5. 看 [ModelRoutingService.java] 的 `generate`，按“排序 → tryAcquire → invoke → markFailure/markSuccess”阅读。
6. 看 [ManagedChatModel.java] 的 `tryAcquire`、`markFailure` 和 `markSuccess`，理解三态变化和并发探测限制。
7. 看 [BailianChatModelInvoker.java] 与 [BailianClient.java] 的带 model 重载，确认供应商适配只停留在最底层。
8. 最后回到 [QuestionResponse.java]，确认本课没有修改证据、计划和会话响应的层级。

## 本课边界

本课没有实现分布式熔断、跨实例健康共享、Embedding 路由、SSE 流式中途切换或复杂模型计费策略。当前状态只存在于单个 Spring 进程中；下一步如果并发和实例数继续增加，才会出现 Redis、租约和全局容量控制的真实需求。
