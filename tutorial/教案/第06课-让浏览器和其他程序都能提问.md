# 第 6 课：让浏览器和其他程序都能提问

## 1. 本课状态

本课已经完成。学生通过 VS Code 绿色按钮亲自运行空问题和真实百炼 Happy Path，两个测试均通过；随后完成 commit 和 push，提交为 `10b6fa1 第6课：添加spring框架以供网络访问`，本地与远程已经同步。

## 2. 为什么现在需要这一课

上一课的 RAG 已经能够调用百炼完成“文本向量化 → 本地检索 → 根据证据生成回答”，但只有测试代码或另一段 Java 代码能够调用 `BailianRagAssistant.answer`。浏览器、手机页面和其他语言编写的程序都无法直接使用它。

本课增加一个 HTTP 入口。调用方只需向固定地址提交一段 JSON，服务器就会把 JSON 变成 Java 对象，检查问题是否为空，调用已有 RAG，然后再把回答变回 JSON。空问题会在访问百炼之前返回清楚的错误。

这个需求第一次使 Web 框架有了实际工作，所以现在才引入 Spring Boot Web。当前仍然只有一个问答入口，不拆 Controller、Service、Repository 多模块，也不建立通用响应包装。

## 3. 本课完成标准

- 应用可以作为 HTTP 服务启动。
- `POST /api/questions` 能接收问题 JSON。
- 非空问题能经过真实百炼链路，返回回答正文与证据标题。
- 空字符串或全空格问题返回 HTTP 400 和 `问题不能为空`，不调用百炼。
- 学生能按照下面的顺序读懂一次请求经过了哪些对象和函数。

## 4. 代码阅读顺序

请严格按这个顺序看，不要一上来钻进 Spring 的内部实现。

1. 先看 `pom.xml` 的 `dependencies` 和 `spring-boot-maven-plugin`。只回答一个问题：本课为了启动 HTTP 服务、校验输入和做完整测试，分别增加了什么能力？这里不需要阅读下载下来的依赖源码。
2. 看 `RagentApplication.java`，依次看类上的 `@SpringBootApplication`、`main`、`bailianClient` 和 `bailianRagAssistant`。回答：应用从哪里启动，已有对象怎样交给 Web 层？
3. 连续看 `QuestionRequest.java`、`QuestionResponse.java` 和 `ApiError.java`。回答：请求、成功响应和失败响应三种 JSON，在 Java 中分别长什么样？
4. 看 `QuestionController.java`，重点看构造函数和 `ask`。这是本课 Happy Path 的中心：HTTP 请求怎样进入已有的 `BailianRagAssistant.answer`，内部结果又怎样变成对外响应？
5. 看 `ApiExceptionHandler.java` 的 `handleValidation`。回答：为什么空问题没有进入 `ask`，最后仍能得到稳定的 400 JSON？
6. 最后看 `QuestionApiLiveIT.java`。先看两个测试方法，再看底部的 `postJson` 辅助函数。沿真实请求数据读完整流程；不用研究 Spring 测试框架内部代码。

每个新增函数上方都有中文函数级注释。先读注释里的“作用、参数、返回值和边界”，再读函数体，会比逐行猜语法轻松许多。

## 5. 主要流程

```mermaid
flowchart LR
    A[调用方发送问题 JSON] --> B[内置 Tomcat 接收 HTTP]
    B --> C[Spring 把 JSON 转成 QuestionRequest]
    C --> D{@Valid 检查 question}
    D -- 空白 --> E[ApiExceptionHandler]
    E --> F[HTTP 400 + ApiError JSON]
    D -- 非空 --> G[QuestionController.ask]
    G --> H[BailianRagAssistant.answer]
    H --> I[百炼 Embedding 三次]
    I --> J[本地 VectorSearch 选 Top-1]
    J --> K[百炼 Chat 生成回答]
    K --> L[KnowledgeAnswer]
    L --> M[QuestionResponse]
    M --> N[HTTP 200 + 回答 JSON]
```

Spring Boot 启动时会创建内置 Tomcat，因此我们不需要另外下载或配置 Tomcat。请求到达后，Spring 根据地址找到 `QuestionController.ask`，把请求正文中的 JSON 转成 `QuestionRequest`，并执行参数校验。

非空问题进入 `ask`。Controller 没有重新实现 RAG，只把问题和当前两条知识交给上一课的助手。助手依次生成两条知识向量和一个问题向量，在本地选出最相近知识，再让聊天模型依据这条知识回答。最后，Controller 将内部的 `KnowledgeAnswer` 转成给调用方看的 `QuestionResponse`。

空问题走另一条路。`@Valid` 在 `ask` 真正执行前发现 `@NotBlank` 不满足，Spring 抛出参数校验异常。`ApiExceptionHandler` 把异常里的中文消息取出，返回 HTTP 400。由于 `ask` 没有执行，这条路径不会产生模型调用和费用。

## 6. 用真实测试数据走一遍 Happy Path

### 6.1 调用方发给本项目的输入

测试向本地随机端口发送：

```http
POST /api/questions
Content-Type: application/json

{"question":"东西不想要了，几天能退？"}
```

Spring 将它转为：

```text
QuestionRequest[
  question = "东西不想要了，几天能退？"
]
```

`@NotBlank` 检查通过，`QuestionController.ask` 开始执行。

### 6.2 Controller 交给 RAG 的数据

问题是：

```text
东西不想要了，几天能退？
```

当前知识列表有两条：

```text
知识 1：
  标题 = 退货政策
  正文 = 签收后 7 天内可申请无理由退货。

知识 2：
  标题 = 保修政策
  正文 = 电子产品自购买之日起享受 1 年保修。
```

`keywords` 是早期关键词问答留下的数据，当前向量 RAG 不使用它；我们没有为了本课把旧课程代码重写掉。

### 6.3 Embedding 模型先后看到的输入和输出

`BailianRagAssistant.answer` 会调用三次 Embedding。三次请求使用相同格式，只是 `input` 不同。

第一次：

```json
{
  "model": "text-embedding-v4",
  "input": "退货政策\n签收后 7 天内可申请无理由退货。"
}
```

第二次：

```json
{
  "model": "text-embedding-v4",
  "input": "保修政策\n电子产品自购买之日起享受 1 年保修。"
}
```

第三次：

```json
{
  "model": "text-embedding-v4",
  "input": "东西不想要了，几天能退？"
}
```

每次响应的关键位置都是：

```json
{
  "data": [
    {
      "embedding": [0.0123, -0.0456, "……很多维数字……"]
    }
  ]
}
```

这里的具体小数由模型生成，每次运行不要求完全一样。`BailianClient` 从 `data[0].embedding` 取出数字并转成 `double[]`。Embedding 模型只看见单段文字并返回向量；它没有看到其他两段文字，也不负责挑选知识和组织自然语言答案。

### 6.4 本地检索的中间数据

程序把两条知识分别和各自的向量组成两个 `EmbeddedKnowledge`，然后用问题向量逐个计算余弦相似度：

```text
问题向量 vs. 退货政策向量 → 相似度 A
问题向量 vs. 保修政策向量 → 相似度 B
A 大于 B                   → Top-1 是“退货政策”
```

具体相似度会随模型输出变化，因此测试不硬编码小数。真正重要的中间状态是 Top-1 证据：

```text
KnowledgeEntry[
  title = "退货政策",
  content = "签收后 7 天内可申请无理由退货。"
]
```

检索发生在本项目进程内，百炼的 Embedding 模型不会替我们执行这一步。

### 6.5 Chat 模型看到的完整输入

本地检索完成后，`BailianClient.generateAnswer` 才发起 Chat 请求。其关键 JSON 是：

```json
{
  "model": "qwen-plus-latest",
  "messages": [
    {
      "role": "system",
      "content": "你是企业知识助手。只能根据提供的证据回答；证据不足时必须明确说不知道。"
    },
    {
      "role": "user",
      "content": "问题：东西不想要了，几天能退？\n\n证据标题：退货政策\n证据正文：签收后 7 天内可申请无理由退货。"
    }
  ],
  "max_tokens": 300
}
```

聊天模型没有看见保修政策的内容，也没有看见相似度分数。它只得到系统约束、原问题和本地选出的退货证据。响应中真正被本项目读取的位置是：

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "签收后 7 天内可以申请无理由退货。"
      }
    }
  ]
}
```

回答的具体措辞可能变化，测试只要求回答不为空，并检查来源一定是 `退货政策`。

### 6.6 最终返回给调用方的数据

内部先得到：

```text
KnowledgeAnswer[
  content = "签收后 7 天内可以申请无理由退货。",
  sourceTitle = "退货政策"
]
```

Controller 随后构造：

```text
QuestionResponse[
  answer = "签收后 7 天内可以申请无理由退货。",
  sourceTitle = "退货政策"
]
```

Spring 再把它转换为 HTTP 响应 JSON：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "answer": "签收后 7 天内可以申请无理由退货。",
  "sourceTitle": "退货政策"
}
```

`KnowledgeAnswer` 是业务内部数据，`QuestionResponse` 是对外接口数据。当前两者虽然很像，仍各自表达清楚边界；这里没有再建立一层通用转换框架。

## 7. 空问题流程中的数据和状态

测试发送：

```json
{"question":"   "}
```

数据变化如下：

```text
原始 JSON
→ QuestionRequest[question = "   "]
→ @NotBlank 校验失败
→ MethodArgumentNotValidException
→ FieldError 默认消息 = "问题不能为空"
→ ApiError[message = "问题不能为空"]
→ HTTP 400 + {"message":"问题不能为空"}
```

这条路径不会进入 `QuestionController.ask`，所以不会创建知识向量、不会请求 Chat，也不会消耗百炼额度。这也是把输入校验放在 Web 边界上的直接价值。

## 8. 第一次出现的 Spring/Java 写法

### 8.1 注解是什么

`@SpringBootApplication`、`@RestController` 和 `@PostMapping` 等 `@...` 写法叫注解。可以先把注解理解为“贴给 Spring 看的标签”：普通 Java 调用仍然执行函数体，而 Spring 会先读取标签，知道哪些类需要创建、哪个函数处理哪个 HTTP 地址，以及调用函数前要做哪些工作。

- `@SpringBootApplication`：这是应用启动配置所在的类；Spring 从 `com.shitan.ai` 包开始扫描组件。
- `@Bean`：请 Spring 调用这个函数，并保存其返回对象。`bailianClient` 先产生客户端，`bailianRagAssistant` 的参数再取得同一个客户端。
- `@RestController`：这个类负责接收 HTTP 请求，函数返回值应写成响应正文。
- `@RequestMapping("/api/questions")`：为整个 Controller 设置共同地址。
- `@PostMapping`：`ask` 处理上述地址上的 POST 请求。
- `@RequestBody`：从 HTTP 正文读取 JSON，并转换成 `QuestionRequest`。
- `@Valid`：转换成功后，执行请求对象上的校验规则。
- `@NotBlank`：字符串不能为 `null`、空字符串或只含空白字符。

### 8.2 Spring 容器和构造函数注入

`RagentApplication` 创建的 `BailianRagAssistant` 会被 Spring 保存。创建 `QuestionController` 时，Spring 发现构造函数需要这个类型，便自动把已有对象传进来。这叫依赖注入。

它在本课解决的具体问题很小：Controller 不必自己读取 API Key，也不必在每个请求中反复 `new BailianClient`。当前没有接口或多实现，所以直接注入具体类。

### 8.3 自动 JSON 转换与 Jackson 的分工

上一课的 `BailianClient` 主动使用 Jackson 2：`ObjectNode` 构造百炼请求，`readTree` 读取百炼响应。本课 Controller 中看不到这些调用，因为 Spring Web 的消息转换器会根据 `Content-Type: application/json` 自动完成“JSON ↔ record”。

因此有两条不同边界：

```text
调用方 JSON ↔ Spring Web ↔ QuestionRequest / QuestionResponse
百炼 JSON   ↔ BailianClient 中显式的 Jackson API ↔ JsonNode
```

两者都处理 JSON，但第一条由 Web 框架自动完成，第二条仍由我们的模型客户端明确控制协议路径。

### 8.4 `ResponseEntity<ApiError>`

普通 Controller 返回 `QuestionResponse` 时，Spring 默认使用 200。错误处理函数还需要明确选择 400，所以返回 `ResponseEntity<ApiError>`：泛型中的 `ApiError` 是正文类型，`badRequest()` 选择状态码 400，`body(...)` 放入正文对象。

### 8.5 全局异常处理注解

- `@RestControllerAdvice`：让一个类统一处理 Controller 抛出的异常，并把结果写成响应正文。
- `@ExceptionHandler(MethodArgumentNotValidException.class)`：这个函数只接参数校验异常。

当前只处理已经明确出现的空问题。网络错误、限流等异常要等对应需求出现后再设计，不提前制作庞大的异常编号体系。

### 8.6 真实 Web 集成测试注解

- `@SpringBootTest(webEnvironment = RANDOM_PORT)`：启动完整 Spring 应用和真实内置服务器，但让系统选择一个空闲端口，避免测试占用固定 8080。
- `@LocalServerPort`：把实际端口写进测试字段 `port`。

测试随后使用 JDK 自带的 `HttpClient` 发真实 HTTP 请求。它不是直接调用 Controller，因此 JSON 解析、路由、校验、异常映射和响应序列化都会实际经过。

测试代码没有显式调用 `RagentApplication.main`，但服务仍然启动，这是 `@SpringBootTest` 在测试生命周期中完成的。点击绿色测试按钮后，顺序是：

```text
VS Code Java Test Runner 启动 JUnit
→ JUnit 读取 @SpringBootTest
→ Spring 找到带 @SpringBootApplication 的 RagentApplication
→ 创建 Spring 容器
→ RANDOM_PORT 要求启动内置 Tomcat，并向系统申请空闲端口
→ @LocalServerPort 将实际端口写入测试字段
→ 最后才执行 @Test 方法
```

日志中的 `Tomcat initialized with port 0` 表示“请操作系统分配空闲端口”，不是最终监听 0 端口；稍后的 `Tomcat started on port 具体数字` 才是实际端口。正常运行应用时，则由 `main` 中的 `SpringApplication.run` 显式启动同一套 Spring 容器和 Tomcat。

### 8.7 为什么此时选择 Spring，以及 Spring 与 Spring Boot 的区别

Java 自己也能建立 HTTP 服务，例如使用 JDK `HttpServer` 或直接编写 Servlet。但是本课已经同时需要启动服务器、匹配 URL、读取请求体、转换 JSON、校验参数、设置状态码、处理异常和启动完整 Web 测试。手工完成这些工作会产生大量与 RAG 主线无关的基础设施代码。

因此选择 Spring 不是因为“Java 做不到”，而是当前真实需求已经足以让成熟 Web 框架承担一组明确工作：

| 当前代码 | 框架承担的工作 |
|---|---|
| `@SpringBootApplication` | 找到应用配置并扫描组件 |
| `SpringApplication.run` | 创建容器并启动内置 Tomcat |
| `@Bean` | 创建并保存百炼客户端与 RAG 助手 |
| Controller 构造函数 | 自动传入它需要的对象 |
| `@RestController`、`@PostMapping` | 把 URL 和 Java 函数对应起来 |
| `@RequestBody` | 把请求 JSON 转成 Java record |
| `@Valid`、`@NotBlank` | 在业务执行前检查问题 |
| `@RestControllerAdvice` | 把校验异常转换成稳定的 HTTP 响应 |
| `@SpringBootTest` | 测试时加载完整应用并启动真实服务器 |

框架没有替我们实现 RAG。向量化、检索、证据选择和模型问答仍由 `BailianRagAssistant`、`VectorSearch` 和 `BailianClient` 完成；Spring 管理的是这些业务对象周围的应用运行环境。

日常常把二者统称为 Spring，但当前可以这样区分：

```text
Spring Framework
├── Spring 容器与依赖注入
├── Spring MVC
├── 参数校验与异常处理
└── 其他基础框架能力

Spring Boot
├── 自动组合常用 Spring 能力
├── 提供 Starter 依赖与版本管理
├── 自动配置 Web 组件
├── 内置 Tomcat
└── 让应用可以直接运行和测试
```

`@RestController` 和后续课程使用的 `SseEmitter` 属于 Spring MVC；`SpringApplication.run`、Starter、自动配置和内置服务器主要由 Spring Boot 提供。它们带来便利，也让一部分调用从显式代码变成框架根据注解触发的生命周期，所以学习时既要知道“注解做什么”，也要知道“它在什么时候替我们调用了什么”。

## 10. 你现在怎样运行测试

先在 VS Code 中打开 `QuestionApiLiveIT.java`，按第 4 节的顺序读完代码。然后打开“终端 → 新建终端”，确认提示符所在目录是 `ragent-st`，执行：

```bash
mvn clean test
```

预期看到：

```text
Tests run: 11, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

为什么只有 11 个？`QuestionApiLiveIT` 以 `IT` 结尾，普通 Surefire 约定不会自动运行它。这避免日常 `mvn test` 每次都访问真实百炼。

然后执行本课两个完整流程测试：

```bash
mvn -Dtest=QuestionApiLiveIT test
```

这会启动真实本地 Web 服务。其中 Happy Path 会调用三次 Embedding 和一次 Chat，使用真实百炼额度；空问题测试不会调用模型。预期最后看到：

```text
Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
HTTP 证据来源：退货政策
```

回答文字可能不同，不必逐字一致。失败时请把第一段 `Caused by`、HTTP 状态码与百炼错误正文发给老师，不要发送 API Key。

你也可以点击测试方法左侧的绿色小三角分别运行两个方法。因为 VS Code Java 测试进程依赖上一课配置的 Server 环境，若终端成功而绿色按钮找不到 Key，先完全重启 WSL 中的 VS Code Server，再重新打开项目。

Tomcat started on port 8080 (http)

```

```

应得到 `HTTP/1.1 200`，正文里有 `answer` 和 `sourceTitle`。再检查空问题：

```bash
curl -i -X POST http://localhost:8080/api/questions \
  -H 'Content-Type: application/json' \
  -d '{"question":"   "}'
```

应得到：

```text
HTTP/1.1 400
...
{"message":"问题不能为空"}
```

实验结束后回到运行服务的终端按 `Ctrl+C`；如果使用 VS Code 绿色按钮，则点击调试工具栏的红色停止方块。

## 12. 本课边界

- 知识仍暂时写在 Controller 中，因为本课只解决 HTTP 入口；数据库和知识管理尚无需求。
- 每次问题仍会重新生成两条知识向量，这个性能问题留待真实规模需求推动。
- 当前是普通一次性 JSON 响应，不做流式输出。
- 当前只有一个真实百炼客户端，不创建 Provider 或多模型路由。
- 已有 Stub 测试只作为第 5 课历史回归。本课使用真实本地服务器和真实百炼 Happy Path，不新增模型 Stub。
- 本课测试用两个方法覆盖完整成功路径与重要的输入边界，不为了测试最小职责拆成大量小用例。
