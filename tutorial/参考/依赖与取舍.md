# 依赖与教学取舍

## 1. 原项目关键依赖及位置

| 依赖/组件 | 原项目解决的问题 | 教学版本策略 |
|---|---|---|
| Java 17 + Maven | 编译、依赖与测试生命周期 | 从第 1 课保留 |
| JUnit 5 | 需求可执行化与回归保护 | 从第 1 课保留；第 6 课由 Spring Boot 测试 Starter 统一提供 |
| Spring Boot WebMVC | HTTP API、参数校验、SSE | 第 6 课因浏览器和其他程序需要真实 HTTP 入口而引入；当前只使用 JSON API 与校验 |
| OkHttp/Jackson | 调模型 HTTP 与 JSON/SSE | 第一次接聊天/Embedding 模型时按需直接使用，不先建多厂商层 |
| PostgreSQL + MyBatis-Plus/JDBC | 文档、Chunk、会话、状态与配置持久化 | 数据需要跨重启保留后引入；先保持单模块与少量表 |
| pgvector 或 Milvus | 大规模向量存储和近邻检索 | 先用内存向量理解相似度，再因数据量和持久化引入一种后端；不首日支持两种 |
| Redis/Redisson | 公平队列、信号量、分布式锁、上下文协调 | 单实例并发问题出现后才引入；先让本地方案暴露多实例缺陷 |
| RocketMQ | 文档异步处理和事务消息 | 先用进程内异步任务；只有需要跨进程可靠消费时再升级 |
| Apache Tika/CommonMark | 多格式与结构化文档解析 | 先支持纯文本，第二种格式到来后再引入/拆解析职责 |
| Elasticsearch | 关键词召回 | 课程保留关键词通道思想，但默认可用 PostgreSQL/内存倒排实现，避免额外集群 |
| Rerank 模型 | 对融合候选重新判断相关性 | 多路召回产生排序问题后引入 |
| AgentScope | ReAct 循环、状态、工具和中间件 | 课程末段固定工作流无法应对开放任务后引入 |
| MCP Java SDK | 标准化发现和调用外部工具 | 已有两个以上外部工具/服务后引入，避免先讲协议后找需求 |
| OpenTelemetry/Langfuse | Agent 和模型链路追踪 | 先实现轻量内部 Trace；外部平台只作为可选扩展与部署练习 |
| S3/OSS | 原文与解析资产存储 | 先用本地文件；部署/多实例时再换对象存储 |
| React/Vite | 用户端与完整管理台 | 不作为主教学代码；用 API/SSE 客户端验收，末段仅给集成边界 |

## 2. 保留、压缩与省略

| 原项目内容 | 决策 | 原因 | 损失与接受理由 |
|---|---|---|---|
| 文档解析、分块、Embedding、索引 | 保留 | 是知识进入系统的核心数据链 | 会先只支持纯文本，格式逐渐增加 |
| 固定 RAG 问答管线 | 保留 | 最易建立检索与生成的心智模型，也是 Agent 知识工具的基础 | 不复制最终 10 余个协作类，从直线代码演化 |
| 来源引用、会话、SSE、取消 | 保留 | 直接影响用户可信度和体验 | 推荐追问等次要事件可省略 |
| 多知识库、改写、意图、多路召回、融合、精排 | 保留并压缩 | 是从 Demo 到可用 RAG 的关键质量演化 | 图谱和联网通道只解释扩展位，不完整实现集群 |
| 模型路由、首包探测、熔断降级 | 保留核心机制 | 外部模型不稳定是生产真实问题 | 只接两种可替代实现，不复刻所有供应商客户端 |
| 异步摄取、状态与可靠投递 | 保留演化过程 | 适合学习异步、任务状态和一致性 | 先本地执行器，是否升级 MQ 由多实例需求推动 |
| 基础 ReAct + 知识/MCP 工具 + 写操作确认 + Skill | 保留并压缩 | 体现 Agentic RAG 与普通工作流区别 | 仅一条清晰任务链，不复制复杂事件桥与全部中间件 |
| Agent 三层上下文与长期记忆仲裁 | 省略生产级实现 | 事务、容量、并发、压缩叠加，远超主线学习成本 | 只保留会话状态与简化摘要；损失跨会话个性化记忆 |
| 完整管理后台 CRUD 与 React 页面 | 省略 | 样板多、对 RAG 心智模型贡献低 | 损失可视化操作体验；API 和测试仍覆盖业务 |
| 用户、角色、Sa-Token、业务审计全套 | 压缩 | 所有权和审计概念重要，但完整 CRUD 不是核心 | 使用简化身份；不覆盖生产权限体系 |
| 远程文档定时刷新状态机 | 省略 | 是高价值但相对独立的运维支线 | 损失 cron、租约锁、etag 刷新实践，不影响核心问答闭环 |
| PDF 视觉解析、MinerU、图片资产 | 省略或选讲 | 外部服务和格式边界复杂 | 保留解析器演化思想，不承担 SaaS 可用性 |
| 历史数据库升级、兼容字段、平台兜底 | 省略 | 属已有生产历史，不应倒灌到从零课程 | 教学项目不兼容原项目历史数据 |
| Dashboard、推荐问题、样例初始化器 | 省略 | 不是最重要 Happy Path | 损失运营便利，不影响核心能力 |

## 3. 教学版本最终边界

最终目标是一套可运行、可测试、可配置、可部署的后端教学项目，能演示：

```text
文本知识进入
→ 解析与分块
→ 向量/关键词索引
→ 问题改写与作用域选择
→ 多路召回、融合与精排
→ 有证据的模型回答
→ 会话、流式、取消、来源
→ 异步任务与可靠性
→ 基础 Agent 自主选择知识或外部工具
```

它不会追求与原项目类名、包层级和基础设施数量一致。只有当课堂上的旧实现已经因真实需求变难维护，才会产生接口、实现选择、模块拆分和配置层。

## 4. 第 1 课为何只有 JUnit

第 1 课的现实需求只是：让程序针对一条已知政策答对问题，并对未知问题诚实返回未找到。Java 标准库已经足够，JUnit 用于先把需求写成可执行例子。Spring、数据库、模型、Repository、Provider 等此时没有问题可解决，加入它们只会遮住第一条数据流，所以明确不引入。

## 5. 第 6 课为何现在引入 Spring Boot Web

第 5 课结束后，RAG 只能被测试或 Java 代码直接调用，浏览器和其他程序没有稳定入口。第 6 课的 HTTP API、JSON 自动转换、输入校验和内置服务器正好由 Spring Boot WebMVC 解决，因此这时引入不再是预先设计。当前不启用数据库、安全框架、SSE 或多模块拆分；这些能力仍需等待后续真实需求。
