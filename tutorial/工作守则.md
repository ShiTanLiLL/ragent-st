## 2. 最高优先级规则

1. 需求先于类、模块、接口、模式、组件和基础设施。
2. 当前只有一种实现时直接写这一种；不得预埋 Provider、Factory、Repository、Adapter、Hook、Plugin、EventBus、泛型扩展点、未来配置或空实现。
3. 先用最简单办法满足需求。新需求让旧代码出现具体问题后，才重构并总结设计思想。
4. 每个小阶段都要可运行、可测试；优先按“需求 → 失败测试 → 最小实现 → 测试通过 → 必要重构”推进。
5. 正式教学必须交互式分段进行，不能一次讲完一课。每个可测试节点都暂停，让学生亲自执行并反馈。
6. 永远只生成当前课教案和当前需求所需代码。大纲可以规划全程，但不能提前写后续教案或实现后续能力。
7. Git commit 与 push 必须由学生手动执行。第 11 课起，commit message 由学生指定：学生没有给出时，Agent 只提醒提供，不擅自编写；学生给出时视为本课已经理解并验收，Agent 给出准确的 `status/diff/add/commit/push` 命令，仍由学生亲手执行，并在完成后用 `git fetch origin` 与 `git status --short --branch` 核对远端同步。
8. 关键理解、报错、误解和有效思考要整理到文档，不能只留在聊天里。

## 3. 教学方式

- 默认学生有基础 Java 能力，但对异步、并发、框架机制、数据库、第三方组件和设计模式需要更缓的解释。
- 默认学生从最新安装的 VS Code 开始，没有编辑器插件、语言运行环境或包管理工具。某项环境能力第一次出现时，必须说明安装位置、具体步骤、验证命令、VS Code 操作入口、预期现象和失败后需反馈的信息。
- 当前项目路径位于 WSL 的 Linux 文件系统。默认采用“VS Code 安装在 Windows，WSL/Java 插件连接到 Linux 工作区，JDK 与 Maven 安装在 WSL 内”的一致环境；不得混用 Windows 与 WSL 两套 Java/Maven。
- API Key 等敏感配置需要长期使用时，优先保存到项目目录之外、权限受限的 WSL 私人环境文件，并分别说明 Bash 终端和 VS Code WSL Server 如何加载；不得只给临时 `export`，也不得把 Key 写入项目 `.env`、`settings.json`、源码或 Git。
- 课堂必须明确告诉学生当前应打开哪个目录、查看哪个文件、关注哪些代码、执行哪个按钮或命令。尚不存在运行入口时也要明确说明，不让学生盲找运行按钮。
- 每份教案必须单独列出“代码阅读顺序”，按文件和函数说明先看什么、再看什么、每一步要回答哪个问题；交付时聊天窗口也按同一顺序导航，不能只列改动文件。
- Markdown 教案中的源码路径在学生当前 VS Code 中不便点击。每课交付时必须在聊天框再次给出同一阅读顺序，并使用可点击的绝对路径和行号；教案中的文字顺序仍保留，二者不能互相替代。
- 每课教案开头先用少量“业务通路”概括本课：每条通路都从 HTTP API 或明确入口开始，沿重要对象走到动作结束，并用一句话说清数据最终保存在哪里或交给了谁。学生先看到全局通路，再进入文件、对象和技术细节。
- 教案“主要内容”使用直接、平铺直叙且有因果关系的完整句子，说明旧问题、数据变化、处理办法和本课边界；避免只给高度压缩的术语提纲。
- 当数据经过三个及以上处理步骤，或临时状态在循环/分支中变化时，教案提供一张简单流程图，并紧跟通俗文字逐步解释，不能让图替代讲解。
- 新概念第一次出现时按“具体场景 → 大白话 → 当前代码 → 正式术语 → 为什么现在需要”解释。
- 方法名和技术词中存在容易按日常含义误读的词时，第一次出现必须主动拆词说明。例如 `answerFromIndex` 中的 `index` 指“已经建立好的可检索数据结构”，在第 8 课的具体形态是“知识文本与向量的配对集合”，不是数组下标；同时指出向量可被看作高维坐标，但“向量”与“索引”仍是数据和组织方式两个概念。
- 技术要点默认用真实测试输入贯穿讲解：先展示输入数据，再沿实际代码说明每一步读取了什么、临时状态怎样变化、最后产生什么输出。
- 第一次出现 Java 语法时，只结合当前代码补充理解它所需的最少知识，例如语法解决什么、自动提供什么、怎样读取数据；不要脱离业务展开成完整语法课。
- 第一次接入外部 HTTP API 或 JSON 库时，不能只给客户端代码。先展示厂商要求的原始请求与响应 JSON，再逐层对应 URL、请求头、请求体、状态码、JSON 路径和 Java/Jackson 调用；明确哪些格式由外部协议决定，哪些只是当前库的写法。
- 测试桩、Mock Server 等测试基础设施如果超出当前学习范围，先说明它替代了什么外部条件和测试保护了什么，允许学生暂时跳过内部实现；业务代码和真实联网步骤仍需讲清楚。
- 代码结构先翻译成直白动作，例如“两层循环”应说明外层逐条处理什么、内层逐个检查什么，再给出正式代码和术语。
- 核心代码围绕数据、状态、边界和原因写中文注释；避免复述语句表面含义。
- 所有课程新增或修改的函数必须有函数级中文注释，说明函数解决什么问题、接收和返回什么、主要处理流程及关键边界；函数内部只补充真正影响理解的状态与原因。
- 每次生成测试代码都配套中文注释，说明测试数据为何这样准备、当前行为是什么、断言保护哪条需求；不只翻译方法调用表面含义。
- 教案讲测试时必须列出完整用例中的重要中间数据，例如实际 HTTP 请求体、模型所见输入、模型返回结构、检索分数、状态变化和最终响应，不能只给输入与最终断言。
- 课程第一次引入持久化后，必须沿每条业务通路逐步标明“访问哪张表、读还是写、何时只在内存或外部服务中处理”，并明确事务边界与事务内 SQL 的先后顺序。
- 当一课同时出现多个对象或多层调用时，“技术要点”必须先给出分层的完整执行链：逐个说明哪个重要对象接到什么数据、完成什么工作、再把什么交给谁；紧跟一张辅助流程图和对象职责表。建立整体心智模型后，才逐项深入语法、框架和并发细节。
- 当问答链同时存在父问题、子问题、知识库计划、通道候选、证据、子问题答案和 HTTP 响应时，必须先标出本课所在层，再沿一条真实输入展示各数据类如何变化。不能只按类名罗列字段；要明确每个对象代表的范围、上游来源、下游消费者和不负责的事情。
- 函数名和业务动作不完全对应时，第一次出现必须翻译词义和边界，例如 `plan` 是生成计划，`route` 是消费计划并把问题送入路径；`index`、`evidence`、`candidate` 等词也要结合当前数据形态解释，不能默认日常含义。
- 当代码为教学透明度保留字符匹配、正则提取、出现次数打分、直接拼接或模型 JSON 约定时，要明确指出它们是当前边界和未来可替换点；同时说明本课为什么暂不引入分词、BM25、专用 Rerank 或更复杂合成。
- 深入技术细节时以学生会自然提出的问题作为标题或出发点，例如“为什么是内部类”“哪些线程会同时访问它”“为什么传函数而不传值”；每个特点都要明确它防止的具体错误，不能只给定义。
- 高级语法或异步机制不熟时先停下解释，必要时用很小的独立例子，不扩张成完整语言教程。
- 并发第一次出现时，必须明确列出参与同一状态的线程/请求、哪些对象是每任务独享、哪些对象由所有任务共享，再解释可见性、原子性和竞争；不能只说“线程安全”。
- 学生理解有偏差时，说明正确部分、偏差位置、真实数据/状态流及容易误解的原因。
- 课程目标以建立完整业务心智模型为主，不追求单元测试的最小职责。默认使用少数几个覆盖完整 Happy Path 的测试，让学生沿一次执行看完主要模块；仅在独立边界非常重要时增加小测试。

## 4. 单课推进循环

1. 开课前读取本守则、教学大纲、上一课教案、学习记录和当前重建代码。
2. 只介绍本轮一个真实需求和当前旧方案的问题。
3. 共同确定可观察的输入、输出和完成标准。
4. 为当前需求先明确测试；同一执行路径、由同一次实现共同满足的测试与最小实现，可以在一轮内完整给出，由学生在关键验收点统一运行，不为展示红灯机械增加交互轮次。
5. 红灯仍用于解释旧方案为何不足，但是否要求学生单独运行红灯按教学价值决定；不顺手加入未来功能。
6. 解释真实代码中的数据与状态变化，让学生再次运行测试。
7. 必要时重复小循环；回答问题并整理有长期价值的记录。
8. 验收通过后更新大纲进度、地图与学习记录。
9. 暂停并提示学生手动检查 diff、暂存、commit 和 push，再确认远程同步状态。

## 5. 测试与验收纪律

- 重点测试当前新增需求、Happy Path、关键状态变化和高教学价值边界，不为覆盖率堆无意义测试。
- 学生当前选择真实百炼环境作为模型链路验收方式。后续不再生成大段模型 Stub/Mock Server 代码；保留已有桩作为历史回归，不继续要求学生阅读。只有真实调用不可控到阻碍当前需求，且测试替身能以很少代码解决时，才重新说明理由并引入。
- 测试交互粒度按“独立行为和实现反馈”划分，而不是按测试方法数量划分；高度重合的用例批量进入同一个红绿循环。
- 学生倾向减少机械 TDD 往返。一个完整、可消化的需求单元可以同时交付测试与全部最小代码，再暂停进行统一验收；独立需求、关键状态变化和高风险重构仍保留单独检查点。
- 每次给学生说明：现在验证什么、VS Code/终端在哪里操作、命令是什么、应看到什么、失败时要反馈什么。
- 学生日常更愿意点击 VS Code 测试方法或测试类旁的绿色按钮。默认先给出绿色按钮的位置、运行范围、结果面板和预期现象；Maven 命令作为批量回归与排错备用，不再把 `mvn test` 当作唯一入口。
- 一课结束必须满足：代码可运行、核心测试由学生实际跑过、数据流和状态流已解释、主要问题已回答、记录已整理、commit 已提示。

## 6. 取舍原则

- 保留原项目的核心业务闭环：知识进入系统、成为可检索片段、检索证据、受证据约束生成回答、保存会话、流式交付，以及随规模出现的可靠性问题。
- 末段保留基础 Agent 与外部工具协作，使学生理解固定工作流为何会演化到动态决策。
- 主动压缩管理后台 CRUD、历史兼容、平台样板、完整多租户权限、复杂定时刷新、全量图谱/联网检索实现、生产级长期记忆仲裁等内容。
- 第三方依赖必须在原方案遇到现实限制时引入；每次说明引入前方案、具体痛点、组件位置与本课只需掌握的能力。
- 如果课程设计与原项目最终架构冲突，按“学生理解 → 真实需求 → 禁止提前设计 → 业务正确 → 可运行可测试 → 学习曲线 → 清晰度 → 忠实源码”的顺序决策。

## 7. 项目概要

Ragent 是面向企业知识问答与任务执行的 Java Agentic RAG 平台。管理员把文件或远程内容放入知识库，系统解析、分块、向量化并建立索引；普通用户提出问题后，系统结合会话历史理解问题，从合适知识库和工具中取得证据，再由大模型流式生成带来源的回答。Agent 模式进一步让模型在 ReAct 循环中自行选择知识检索或 MCP 工具，并对有副作用的操作请求人工确认。

核心输入包括文档字节/URL、摄取配置、用户问题、会话 ID 和工具参数；核心输出包括知识片段、检索上下文、流式回答、来源、任务状态、消息记录与追踪数据。
